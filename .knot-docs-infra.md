## 1. Theme choice

**Recommendation: Hugo Book (`alex-shpak/hugo-book`).**

Trade-offs in three sentences:

1. **Hugo Book** — minimal, content-centric, single left-sidebar nav driven by the `content/` tree, ships dark mode + client-side search out of the box; perfect fit for an internal team docs site where the goal is "read the docs, not admire the chrome." Its main limitation — no fancy landing page, no team blog, no card grids — is a **non-issue** for an internal team that just wants navigable prose + diagrams + linked notebooks. Theme is small enough to read end-to-end if we ever need to fork.
2. **Hextra** — newer, gorgeous, has full-text search, dark mode, callouts, and supports MDX-style components; **but** it's optimised for public-facing docs sites and pulls in more JS than Hugo Book. Overkill for an internal team.
3. **Hugo Theme Relearn** — feature-rich (taxonomies, callouts, mermaid, math, advanced print), aimed at large enterprise docs trees; richer than we need at design stage and the visual density is higher than Book.
4. **Docsy** — Google's framework-y theme, requires a postcss/npm toolchain, opinionated about i18n + versioning; way too much machinery for one internal team.

**Decision: Hugo Book.** Revisit only if we hit a concrete limitation (e.g. we want versioned docs against compile hashes — but that's a future problem, not a launch problem).

## 2. Marimo-as-docs integration

**Decision: embed marimo notebooks into the same site as static HTML pages, served alongside Hugo content under a single domain/origin.**

### Why embed, not link out

- Single-team tool — there's no value in a separate notebook host. One thing to deploy, one URL to share.
- Marimo's `marimo export html-wasm` produces a fully self-contained HTML bundle (HTML + JS + WASM runtime + the notebook source) that runs the notebook **in the browser** — no Python server needed. That makes it static-site friendly: just drop the bundle into `public/` next to Hugo's output.
- Sidebar entries should sit next to prose docs so a reader of `core-design.md` can click straight into `02_end_to_end_story` without context-switching to a different host.

### Two flavours of export, pick per-notebook

Marimo can export in two modes — we use both depending on intent:

| Mode | Command | Use when |
|---|---|---|
| **html-wasm (interactive)** | `marimo export html-wasm <nb>.py -o <dest>/ --mode run` | The notebook is a runnable demo and the user expects to edit cells / re-run. Heavier (ships pyodide). |
| **html (static render)** | `marimo export html <nb>.py -o <dest>.html` | The notebook is "executable docs" — render once at build time, ship a static rendered page. Light. |

Default: `html-wasm` for the end-to-end story notebooks (the user wants people to run them), `html` for any utility / one-off notebooks that exist mostly as written narrative.

### How they live alongside Hugo

Hugo by default copies anything under `static/` verbatim into `public/` at build time. We exploit that:

- Build pipeline exports each marimo notebook to `docs/static/notebooks/<name>/index.html` (for html-wasm mode, the bundle becomes a directory with assets).
- Hugo content has a thin Markdown stub per notebook in `content/notebooks/<name>.md` that:
  - sets a sidebar title
  - either iframes the exported notebook (`{{< rawhtml >}}<iframe src="/notebooks/<name>/" ... />{{< /rawhtml >}}`)
  - or links straight to it (`[Open notebook](/notebooks/<name>/)`)
- Sidebar nav (Hugo Book reads from `content/`) picks up the stub automatically — no manual nav file to maintain.

The iframe-vs-link choice per notebook is a content decision, not a build decision. Both work.

### Build ordering

Marimo export must run **before** `hugo build`, because it writes into `static/`, which Hugo copies during its build.

## 3. Build pipeline

Single `scripts/docs.sh` with subcommands. No Makefile (the project doesn't currently use one and a Makefile is one more dialect to maintain). The script lives at `/mnt/main/code/knot/scripts/docs.sh`.

```bash
#!/usr/bin/env bash
# /mnt/main/code/knot/scripts/docs.sh
# Build, serve, and export the knot docs site.
set -euo pipefail

ROOT="$(cd "$(dirname "$0")/.." && pwd)"
DOCS="$ROOT/docs"
NOTEBOOKS="$ROOT/notebooks"
EXPORT_DIR="$DOCS/static/notebooks"

# Notebooks rendered as interactive html-wasm bundles (directories).
WASM_NOTEBOOKS=(
  "01_initial_spec_and_sources"
  "02_end_to_end_story"
)
# Notebooks rendered as a single static .html (none yet, placeholder).
STATIC_NOTEBOOKS=()

build_notebooks() {
  mkdir -p "$EXPORT_DIR"
  for nb in "${WASM_NOTEBOOKS[@]}"; do
    echo ">> exporting $nb (wasm)"
    marimo export html-wasm \
      "$NOTEBOOKS/$nb.py" \
      -o "$EXPORT_DIR/$nb" \
      --mode run \
      --include-cloned-layouts
  done
  for nb in "${STATIC_NOTEBOOKS[@]}"; do
    echo ">> exporting $nb (static)"
    marimo export html \
      "$NOTEBOOKS/$nb.py" \
      -o "$EXPORT_DIR/$nb.html"
  done
}

build_site() {
  build_notebooks
  ( cd "$DOCS" && hugo --minify --cleanDestinationDir )
  echo ">> built: $DOCS/public/"
}

serve() {
  # Hugo's live reload watches content/. Notebook re-exports are manual:
  # re-run `scripts/docs.sh notebooks` in another shell while editing a notebook.
  build_notebooks
  ( cd "$DOCS" && hugo server --buildDrafts --bind 0.0.0.0 )
}

clean() {
  rm -rf "$DOCS/public" "$DOCS/resources" "$EXPORT_DIR"
}

cmd="${1:-build}"
case "$cmd" in
  notebooks) build_notebooks ;;
  build)     build_site ;;
  serve)     serve ;;
  clean)     clean ;;
  *) echo "usage: $0 {notebooks|build|serve|clean}"; exit 2 ;;
esac
```

Sample invocations:

```bash
scripts/docs.sh serve       # local dev, http://localhost:1313
scripts/docs.sh notebooks   # re-export marimo bundles only
scripts/docs.sh build       # full static build into docs/public/
scripts/docs.sh clean       # nuke build artifacts
```

**Deploy-ready output:** `docs/public/`. That dir is the static site. Whatever serves static files (nginx, GitHub Pages, S3+CloudFront, a sidecar `caddy` container in our cluster) just points at it. No CI yet, per the brief.

### 4.1 `design/` content: copy, symlink, or Hugo mounts?

The design docs at `/mnt/main/code/knot/design/` are the source of truth and are written for direct reading via the editor. The docs site needs to surface them too. Three options:

1. **Copy at build time** (`rsync design/ docs/content/design/`). Simple, but two trees to keep mentally aligned.
2. **Symlink** (`ln -s ../../design docs/content/design`). Hugo follows symlinks. Single source of truth. Caveat: links between design docs use repo-relative paths, which may break under Hugo's URL rewriting; we'd need to audit.
3. **Hugo modules / mounts** — `hugo.toml` has a `[[module.mounts]]` block that mounts `../design` into `content/design/` at build. This is Hugo-native, no filesystem trick, and works with `hugo server` live reload across the boundary.

**Recommendation: option 3 (Hugo module mounts).** It's the idiomatic Hugo answer, no symlink fragility, and one source of truth. Sketched in §5.

### 4.2 Theme: submodule, Hugo module, or vendored copy?

Three options for `hugo-book`:

1. **Git submodule** at `docs/themes/hugo-book/`. Standard for Hugo themes, well-understood, but submodules are mildly annoying (clone gotchas, `git submodule update --init --recursive` rituals).
2. **Hugo module** (`hugo mod get github.com/alex-shpak/hugo-book`). Requires `go` on the build host. Cleanest version pinning via `go.mod`.
3. **Vendored copy** (just `git clone` the theme into `docs/themes/hugo-book/`, drop its `.git/`, commit). Simplest to reason about; we can patch freely; updates are manual.

**Recommendation: git submodule.** Standard Hugo practice, no extra Go dependency, theme updates are explicit (`git submodule update --remote`). Add it in bring-up:

```bash
cd /mnt/main/code/knot/docs
git submodule add https://github.com/alex-shpak/hugo-book themes/hugo-book
```

## 5. Config skeleton

`docs/hugo.toml` (described, not yet wired):

```toml
baseURL    = "/"                    # internal-only; no canonical domain yet
languageCode = "en-us"
title      = "knot"
theme      = "hugo-book"

# Disable taxonomies — we don't need tags/categories for an internal team site.
disableKinds = ["taxonomy", "term", "RSS"]

[params]
  # Hugo Book params
  BookTheme       = "auto"          # auto-switches light/dark on OS pref
  BookToC         = true            # right-side TOC for each page
  BookSection     = "docs"          # which content section becomes the sidebar root
  BookSearch      = true            # client-side fuse.js search; fine for our size
  BookEditPath    = ""              # internal repo, no external "edit on GitHub"
  BookRepo        = ""
  BookDateFormat  = "2006-01-02"

[markup]
  [markup.goldmark]
    [markup.goldmark.renderer]
      unsafe = true                 # let us iframe/raw-html notebook embeds
  [markup.highlight]
    style       = "github-dark"
    lineNos     = false
    codeFences  = true

# Mount the design/ tree from the parent repo directly into content/design/.
# This is the §4.1 option-3 trick: single source of truth.
[module]
  [[module.mounts]]
    source = "content"
    target = "content"
  [[module.mounts]]
    source = "../design"
    target = "content/design"
  [[module.mounts]]
    source = "../design/staging"
    target = "content/staging"
  [[module.mounts]]
    source = "../design/_meta"
    target = "content/meta"
  [[module.mounts]]
    source = "static"
    target = "static"
  [[module.mounts]]
    source = "layouts"
    target = "layouts"
```

### Sidebar nav

Hugo Book derives the sidebar from the content tree + each page's `weight` front-matter. No central nav YAML to maintain. Concretely the order will be:

1. **Home** (`content/_index.md`) — orientation: who knot is for, where to start.
2. **Design** (mounted from `../design/`)
   - `goals.md`
   - `core-design.md` — the 17 commitments
   - `knot-as-compiler.md`
   - `source-layer-contract.md`
   - `compiled-workflow-hashing.md`
   - `reification-strategy.md`
   - `trust-and-merge.md`
3. **Staging** (mounted from `../design/staging/`) — alphabetical under each subgroup, weight-ordered for the load-bearing ones (`spec-model`, `pipeline-stages`, `seam-contract-pattern` first).
4. **Notebooks** (`content/notebooks/`) — links into the marimo exports under `/notebooks/<name>/`.
5. **Ops** (`content/ops/`) — `docker-compose.yml`, `scripts/`, how to bring the dev stack up.
6. **Meta** (mounted from `../design/_meta/`) — design-thinking patterns, code-style preferences.

We do **not** mount `legacy/` from design — internal team site, no need to surface superseded material.

### Search

Hugo Book ships fuse.js client-side search (toggled by `BookSearch = true`). For a docs tree this size (a few dozen markdown files + a few notebook stubs), it's plenty. No Algolia, no server-side index.

### Taxonomies

None. `disableKinds = ["taxonomy", "term", "RSS"]` removes them entirely. We don't need tags/categories — the directory structure is the structure.

### One required custom shortcode

`docs/layouts/shortcodes/rawhtml.html`:

```html
{{ .Inner | safeHTML }}
```

Used in notebook stub pages to embed an iframe pointing at the exported marimo bundle, e.g.:

```markdown
---
title: "End-to-end story"
weight: 20
---

A walk from empty database through bandit-learned trust.

{{< rawhtml >}}
<iframe
  src="/notebooks/02_end_to_end_story/"
  style="width:100%; height:80vh; border:0;"
  loading="lazy"
></iframe>
{{< /rawhtml >}}

[Open notebook in its own tab →](/notebooks/02_end_to_end_story/)
```

## 7. Open questions (to resolve before building)

These do not block the design but the user should weigh in before we cut files:

- **Hosting target.** Static `docs/public/` deploys anywhere. Is the intent to ship this as a sidecar in the cluster (a tiny `caddy` or nginx container under `/mnt/cluster/stacks/`), or is it strictly local-build-and-read? Affects only deploy, not build.
- **Notebook freshness policy.** When a notebook changes, do we re-export on every site build (current pipeline), or pin the export to a tagged release? For an internal team site, default = always-fresh is fine; flagging in case the user wants reproducibility tied to compile hashes.
- **Mounting `../design` directly.** This couples the Hugo site to the on-disk layout of `design/`. If `design/` is ever restructured, the docs build breaks until mounts are updated. Acceptable cost for single-source-of-truth, but flagging.
- **Submodule vs vendored theme.** Submodule is the recommendation; if the user dislikes submodules in this repo, vendoring is a one-line swap.
- **`pyproject.toml` cleanup.** Removing `mkdocs-material` from `[dev]` is the right call but it's a separate change from the docs scaffold itself. Bundle or split?

## 8. Summary

- **Theme:** Hugo Book, submoduled at `docs/themes/hugo-book/`.
- **Marimo:** embedded as static exports under `docs/static/notebooks/`, surfaced via thin Markdown stubs in `content/notebooks/`. `html-wasm` mode for interactive end-to-end stories, `html` mode for write-only narratives.
- **Build:** one `scripts/docs.sh` with `notebooks | build | serve | clean`. Marimo exports run before `hugo build`.
- **Layout:** `docs/` holds `hugo.toml`, `content/`, `static/`, `layouts/`, `themes/hugo-book/`, `public/` (gitignored). The `design/` tree is mounted into `content/design/` via Hugo module mounts — single source of truth.
- **Config:** taxonomies off, client-side search on, sidebar derived from the content tree, one custom `rawhtml` shortcode for iframe embeds.
- **Cleanup:** drop `mkdocs-material` from `pyproject.toml` and the stale `site/site/` line from `.gitignore`.
