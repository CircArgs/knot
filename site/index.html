knot is a typed Python compiler for the multi-source MDM problem. You declare classes, slots, FKs, sources, bindings, constraints, virtuals, and vector slots. It emits the postgres SQL: bindings tables per class, per-slot weighted resolved views, an ER cascade that runs in one atomic statement, k-NN candidate queries, and constraint validators with auto-generated FK-chain JOINs. hitch is the reference Temporal + GraphQL + pgvector deployment that proves the substrate is real.

See the fusion model Why it deserves to exist

Multi-source fusion in three relations

This is the most distinctive thing knot does. Every concrete class compiles to one table + two views + one weight table. Together they give you per-slot weighted argmax across sources, full provenance, runtime tunability, and a designated human-correction surface — without ever materializing a separate "golden record" table. The rest of the page builds on this; understanding it makes the wedge obvious.

1. <class>_bindings — one row per (source, source_id)

Every source's claim about a class becomes one row. The canonical_id column gets stamped by ER (NULL pre-ER). Same canonical means "these source-rows are the same real-world entity."

2. source_weight — the runtime-tunable policy table

One row per (source_name, class_name, slot_name, weight). Auto-seeded by emit_weight_seed() at deploy time with sane defaults from the host's dict, then operator-tunable per (class, slot) at runtime via binding.upsert_weight_sql(). Re-deploys preserve operator tuning (ON CONFLICT DO NOTHING). Critically, the auto-bound _user_corrections source is always seeded at 1e6 regardless of the operator's defaults — closes the silent-failure window where forgetting to seed corrections would lose every GraphQL mutation.

3. <class>_resolved — the per-slot argmax view

One row per canonical_id. Each slot is a correlated subquery that picks the highest-weight non-NULL claim across sources, tie-broken alphabetically. Reads weights live from source_weight — no materialization, no scheduled recompute, weight changes flip resolved values on the next read.

View DDL (real emit_resolved_view output)
CREATE VIEW hitch.movie_resolved AS
SELECT
  cb.canonical_id,
  (SELECT b.runtime_minutes
   FROM hitch.movie_bindings b
   LEFT JOIN hitch.source_weight w
     ON w.source_name = b.source_name
    AND w.class_name = 'Movie'
    AND w.slot_name  = 'runtime_minutes'
   WHERE b.canonical_id = cb.canonical_id
     AND b.runtime_minutes IS NOT NULL    -- NULL-skip
   ORDER BY COALESCE(w.weight, 0) DESC,    -- argmax
            b.source_name                  -- alphabetical tie-break
   LIMIT 1) AS runtime_minutes,

  -- … one correlated subquery per slot …

FROM (
  SELECT DISTINCT canonical_id
  FROM hitch.movie_bindings
  WHERE canonical_id IS NOT NULL
) AS cb;

NULL-skip is not an oversight — it's the design

A high-weight source that doesn't have a value for slot X loses to a lower-weight source that does. That's why the inner subquery has WHERE b.<slot> IS NOT NULL before the ORDER BY: NULL means "no claim," not "the claim is NULL." Concrete example using real demo data:

4. <class>_all_sources — full per-slot provenance

One row per canonical_id. Each slot is a jsonb_object_agg over sources that have a non-NULL value, mapping source_name → {value, weight}. This is the audit surface — "why did the resolver pick X for runtime_minutes?"

View DDL (excerpt)
CREATE VIEW hitch.movie_all_sources AS
SELECT
  b.canonical_id,
  jsonb_object_agg(
    b.source_name,
    jsonb_build_object(
      'value',  b.runtime_minutes,
      'weight', COALESCE(w_runtime_minutes.weight, 0)
    )
  ) FILTER (WHERE b.runtime_minutes IS NOT NULL) AS runtime_minutes,
  -- … one jsonb_object_agg per slot …
FROM hitch.movie_bindings b
LEFT JOIN hitch.source_weight w_runtime_minutes
  ON w_runtime_minutes.source_name = b.source_name
 AND w_runtime_minutes.class_name = 'Movie'
 AND w_runtime_minutes.slot_name = 'runtime_minutes'
-- … one join per slot …
GROUP BY b.canonical_id;

The _user_corrections surface

knot auto-creates a synthetic _user_corrections source on every spec, auto-bound to every concrete class. No opt-in. Its weight row is auto-seeded by emit_weight_seed at 1e6 — a dominant ceiling that beats any declared source. Operators can tune per (class, slot) afterward (down to 0 to suppress, up to 1e18 for absolute primacy).

A correction is just a row in the bindings table whose source_name = '_user_corrections'. Writing one through GraphQL's correctMovie(...) mutation dominates the resolver argmax on the next read. retract deletes the row → the next-highest source wins. 

mutation {
  correctMovie(
    canonical_id: "m_bd6c1bef…",
    source_identifier: "ops-fix-2026-05-23",
    runtime_minutes: 100      # override the imdb winner
  ) {
    runtime_minutes           # returns 100 — dominated by corrections weight 1e6
  }
}

What nothing else ships in this combination

Multi-source bindings table + per-slot weighted resolved view + per-source jsonb provenance + runtime-tunable weight policy + auto-dominant corrections surface, all compiled from a typed Python spec. SQLAlchemy and jOOQ would let you build any single piece; none of them give you all five from one declarative source. The "build it in dbt models" alternative is what most teams do, and the cost is drift between five model files every time the spec changes.

The honest competitor landscape

knot doesn't do ER itself. It exposes the SQL primitives (assign_canonicals_sql, find_er_candidates_sql, translate_fks_sql) so a host can do ER with whatever policy fits. That means ER engines (Splink, Senzing, Dedupe, Zingg) aren't competitors — they're consumers: their match decisions feed knot's stamp primitive.

knot's modeling style

knot is schema-as-code with a typed combinator DSL. The phrase is precise — every word is a deliberate position. Peers in this style: SQLAlchemy Core (Python), Ecto (Elixir), Drizzle (TypeScript), Diesel (Rust), Slick (Scala). Distinct from schema-as-config (LinkML YAML, Avro IDL, Protobuf, raw SQL DDL files) where the schema is a foreign artifact and a separate codegen step ferries it into your codebase.

The deliberate choices

Schema-as-code

The spec lives in your application code — importable, type-checked, IDE-refactorable, grep-able. Not in a YAML file the IDE doesn't understand. Renaming a slot is F2 in your editor.

Typed combinator DSL

Operators (>=, &, |, ~) build typed AST nodes. movie.col.year >= 1888 isn't a string — it's a Compare(Ref, Literal) that compiles to SQL via singledispatch visitors.

Compile-target, not runtime-interpreted

knot emits SQL strings — your psycopg connection runs them. Opposite of an ORM that intercepts every attribute write and auto-flushes. Closer to jOOQ + Diesel than SQLAlchemy ORM.

Initial encoding of the AST

The AST is data (frozen dataclasses with slots=True). Multiple compilers walk it — the DDL emitter, the query compiler, the constraint emitter, the ER cascade emitter. Adding a Trino dialect is a new module, not a fork.

Embedded path navigation

movie.col.director.birth_year walks an FK chain via Python attribute access. person.via(credit.col.person) walks an inbound reference. Both compile to JOINs/correlated subqueries automatically.

Imperative build, frozen emit

Mutable builder methods accumulate the spec (spec.add_class("Movie").slot(...)). The compile output is deterministic and pure: same spec → byte-for-byte same SQL.

Where knot differs from peers in this style

SQLAlchemy Core / Drizzle / Ecto give you the typed combinator surface over plain tables. They stop at "typed expressions over columns." knot adds the domain-level vocabulary postgres DDL has nowhere to put: bindings, sources, virtual classes, FK chains in constraints, vector slot types, ER cascade as a primitive. The peer libraries are right that "the table is the model" — but the table isn't the right model for multi-source MDM.

SQLAlchemy Core — what it gives you
movies = Table('movies', metadata,
  Column('id', Integer, primary_key=True),
  Column('title', String),
  Column('year', Integer),
  Column('director_id', ForeignKey('people.id')),
)

select(movies.c.title) \
  .where(movies.c.year >= 1888)   # typed Compare, compiles to SQL

Typed table refs, typed comparisons, typed builders. Stops here.

knot — what it adds above tables
movie = spec.add_class("Movie")
movie.slot("year", types.INTEGER)
movie.slot("director", person)     # FK by Class ref, not column ref
movie.slot("title_embedding",      # Vector type → HNSW index emitted
           types.VECTOR(384, metric="cosine"))

  spec.add_source(src).bind(movie)

  where=movie.col.year >= 2000)

  "director_alive",
  body=movie.col.director.birth_year < movie.col.year,
)

Domain layer above SQL: classes, slots, FK refs, virtuals, multi-source bindings, constraints with FK chains, vector slot types — none of these are postgres DDL concepts.

When you actually want an ORM (not knot)

SQLAlchemy ORM, Django ORM, Hibernate, ActiveRecord — they give you an identity map, unit of work, and auto-flushing dirty-tracked objects. You mutate Python attributes; the ORM emits INSERTs/UPDATEs at commit time. That's the right shape when your domain is OLTP CRUD against your own single-source-of-truth schema — user signs up, edits profile, flushes session. The ORM hides SQL because you mostly don't care about the SQL.

knot is the wrong tool for that. There's no session, no dirty tracking, no auto-persist on attribute write — knot emits SQL strings the host runs. If you'd be happy with user.email = new_email; session.commit(), you don't have an MDM problem and you don't need knot. ORMs are great at OLTP CRUD; knot is for the multi-source fusion + ER + validation compile-target case that ORMs don't model.

knot vs graph databases

Neo4j/Cypher and RDF/SPARQL are graph storage + query engines — your data lives in them. knot is a compiler that targets the postgres you already have. Same query intent, very different category. Worth showing concretely:

Same intent — "directors with more than one director credit":

knot — typed Python AST
(person.resolved
  .where(person
    .via(credit.col.person)
    .where(credit.col.role
           == "director")
    .count() > 1)
  .select(person.col.name))

Compiles to one SQL with a correlated subquery on credit_resolved. Reads against the argmax-fused view. Uses canonical_ids stamped across all three sources.

Neo4j / Cypher
MATCH (p:Person)<-[:HAS_PERSON]-
      (c:Credit {role:'director'})
WITH p, count(c) AS n
WHERE n > 1
RETURN p.name

Compact. But p.name is last-write-wins from whichever import touched it last. Multi-source fusion is your problem. No weight policy.

RDF / SPARQL
SELECT ?name WHERE {
  ?p a :Person ; :name ?name .
  { SELECT ?p (COUNT(?c) AS ?n)
    WHERE { ?c :person ?p ;
                :role "director" }
    GROUP BY ?p }
  FILTER(?n > 1) }

Expressive. But fusing ?name across three sources is three triples or one owl:sameAs-bridged URI. Choosing which name wins is OWL config, not a Python policy.

Forward + reverse navigation in each

One of graph engines' best ergonomic wins is bidirectional edge traversal — person ←HAS_PERSON— credit is as natural as the forward direction. SQL FKs are inherently directional (the column lives on one side), so reverse navigation needs a different syntactic shape. knot exposes it as cls.via(other.col.fk), which compiles to a correlated subquery.

Where each graph paradigm breaks down for multi-source MDM:

Property graphs (Neo4j)
  • ↯No multi-source provenance. A property is one value. Tracking "imdb says 99, tmdb says 100, rt says 99" requires sub-nodes per source per slot — explodes graph cardinality.
  • ↯No declarative weight policy. Which source wins per slot? Write APOC, run on a schedule.
  • ↯ER is manual. MERGE assumes you already cleaned names. Cross-source variants need a separate matching step.
  • ↯Loose schema. FK-chain predicates and correlated-aggregate predicates aren't declarative constraints — they're scheduled queries with alerts.
RDF / SPARQL
  • ↯Open-world assumption. Missing assertions ≠ violations. knot is closed-world — required slot resolving to NULL fires a built-in constraint.
  • ↯ER is owl:sameAs + DL reasoner. Reasoning cost grows with the graph; one knot SQL statement vs minutes of OWL reasoning.
  • ↯Multi-source = named graphs. You manage membership manually; no per-slot argmax across graphs.
  • ↯Embeddings are bolt-on. Vendor extensions exist; not part of the schema language.
When you actually want a graph DB (not knot)

knot's design depends on enumerating your relationships up front as typed FK slots. That assumption is load-bearing — FK chains as attribute access, constraint bodies spanning FKs, GraphQL SDL emitted from the spec, the resolved-view argmax — all require knowing every edge type at compile time. Use a graph DB when that breaks down:

  • →Arbitrary topology with hundreds-to-thousands of relation types you don't enumerate up front. Wikidata-shaped knowledge graphs (11,000+ properties), open-relation-extraction over documents, scientific KGs (biomedicine has hundreds of relation types like inhibits, binds_to, metabolizes), enterprise KGs accumulating relations organically across departments.
  • →Variable-length traversal across unknown predicates. Cypher's -[*1..5]->, SPARQL property paths ?a :p1/:p2/:p3 ?b, Gremlin's .repeat(out()).times(5). You can't write these in knot because you'd have to spell the edge types.
  • →Schema-flexible writes. RDF's "just insert another triple with a new predicate"; knot needs a spec edit + ALTER TABLE.
  • →Reasoning over the graph structure itself. OWL inferencing, subclass chains, transitive closure across unknown predicates.
  • →Federation across remote SPARQL endpoints. Different problem entirely; use a triple store.

The filter is roughly: known classes + small finite set of FK relations (Movie has a director, a studio, some credits — period) → knot. Open-ended graph topology, schema-flexible → Neo4j / RDF.

Queries: three composition shapes, one builder

Relational filters, FK chain walks, and vector k-NN compose in the same Query AST. Below are the three with the SQL they emit — pulled directly from q.sql():

knot query AST
# 1. correlated count — directors with >1 credit
q = (person.resolved
     .where(person.via(credit.col.person)
                  .where(credit.col.role == "director")
                  .count() > 1)
     .select(person.col.name))

# 2. FK chain walk — movies whose director was alive at release
q = (movie.resolved
     .where(movie.col.director.birth_year < movie.col.year)
     .select(movie.col.title, movie.col.director.name))

# 3. k-NN — movies most similar to a target embedding
q = (movie.from_source(imdb)
     .order_by(movie.col.title_embedding.distance_to(target_vec))
     .limit(10))
SQL emitted (real output)
-- 1. correlated subquery on credit_resolved
SELECT hitch.person_resolved.name
FROM hitch.person_resolved
WHERE (SELECT COUNT(*)
       FROM hitch.credit_resolved
       WHERE hitch.credit_resolved.person
           = hitch.person_resolved.canonical_id
         AND hitch.credit_resolved.role = 'director') > 1;

-- 2. FK chain → automatic LEFT JOIN with auto-aliased target
SELECT m.title, movie_director.name
FROM hitch.movie_resolved m
LEFT JOIN hitch.person_resolved AS movie_director
  ON movie_director.canonical_id = m.director
WHERE movie_director.birth_year < m.year;

-- 3. k-NN with the pgvector op picked from the slot's metric
SELECT * FROM hitch.movie_bindings
WHERE source_name = 'imdb'
ORDER BY title_embedding <=> '[0.1, 0.2, ...]'::vector(384)
LIMIT 10;

Why this expressive surface matters

The three shapes compose. You can write a k-NN over the resolved view (cross-source vectors), filter by a multi-hop FK chain, count via an inbound reference, and order by distance — all in one Query. The SQL gets compiled with the right JOINs, the right correlated subqueries, the right pgvector operator from the slot's declared metric. And the typed vocabulary means a typo at movie.col.directr.name raises at that line, not when postgres returns "column does not exist."

Constraints: from declaration to SQL

A constraint body is the same Expr AST as a query .where() clause and a virtual class predicate. One vocabulary, three uses. The compiler walks the body, collects FK chains, emits the right LEFT JOINs, and produces the SELECT that returns offending canonical_ids. Below is a real constraint and its verbatim SQL output:

spec (what you write)
movie.add_constraint(
  "movie_director_alive_at_release",
  body=movie.col.director.birth_year.is_null()
     | movie.col.year.is_null()
     | (movie.col.director.birth_year < movie.col.year),
)

NULL-safe by design: either side NULL → predicate passes (postgres three-valued logic). The FK chain director.birth_year is attribute access on a ClassRef-typed slot; the compiler auto-generates the JOIN.

SQL emitted (verbatim)
SELECT
  'movie_director_alive_at_release' AS rule_id,
  'Movie' AS class_name,
  'error' AS severity,
  NULL AS message,
  hitch.movie_resolved.canonical_id AS offending_pk
FROM hitch.movie_resolved
LEFT JOIN hitch.person_resolved AS movie_director
  ON movie_director.canonical_id
   = hitch.movie_resolved.director
WHERE NOT (
  (movie_director.birth_year IS NULL)
  OR (hitch.movie_resolved.year IS NULL)
  OR (movie_director.birth_year < hitch.movie_resolved.year)
);

LEFT JOIN (not INNER) so rows with NULL FK still surface; the NULL-safe predicate handles them. Run against movie_resolved — checks the fused value, not per-source claims.

What knot gives you here

The same Python expression works as a constraint, a virtual-class predicate, and a query .where() clause. Write movie.col.director.birth_year < movie.col.year once; use it for the constraint and a virtual class (movie.add_virtual("ConsistentMovie", where=...)) and a runtime query. The compiler emits the right SQL for each context. SQLAlchemy's CheckConstraint takes a text string; SHACL needs a SPARQL engine; Cypher constraints don't span paths declaratively.

ER cascade as a single statement

Most MDM stacks orchestrate ER as multiple steps: stamp the row, then translate the FKs, then fan out back-references. knot ships the whole cascade as one atomic statement — a writable-CTE chain. Strictly idempotent on re-run. The host supplies the canonical_id decisions; knot's primitive applies them safely.

binding.assign_canonicals_sql() — real emit
WITH stamp AS (
  -- (1) Stamp canonical_id on unstamped rows of THIS (source, class)
  UPDATE hitch.person_bindings AS b
  SET canonical_id = a.canonical_id,
      er_metadata  = COALESCE(a.er_metadata, b.er_metadata)
  FROM jsonb_to_recordset(%(assignments)s::jsonb)
       AS a(canonical_id text, source_identifier text, er_metadata jsonb)
  WHERE b.source_name = 'imdb'
    AND b.source_identifier = a.source_identifier
    AND b.canonical_id IS NULL          -- idempotency guard
  RETURNING b.canonical_id, b.source_identifier
),
fanout_credit AS (
  -- (2) Backward fan-out: rewrite Credit.person source-ids → canonical-ids.
  -- EXISTS-gated so a no-op stamp can't force-rewrite anything.
  -- Referrers sorted alphabetically so lock-acquisition order is
  -- deterministic across spec construction orders (deadlock-safe).
  UPDATE hitch.credit_bindings AS r
  SET person = COALESCE(
    (SELECT canonical_id FROM stamp WHERE source_identifier = r.person),
    r.person)
  WHERE r.source_name = 'imdb'
    AND EXISTS (SELECT 1 FROM stamp WHERE source_identifier = r.person)
),
fanout_movie AS (
  -- (3) Same fan-out for Movie.director
  UPDATE hitch.movie_bindings AS r
  SET director = COALESCE(
    (SELECT canonical_id FROM stamp WHERE source_identifier = r.director),
    r.director)
  WHERE r.source_name = 'imdb'
    AND EXISTS (SELECT 1 FROM stamp WHERE source_identifier = r.director)
)
SELECT 1;

One statement. One transaction. The host passes a JSON array of {canonical_id, source_identifier, er_metadata}; thousands of stamps per round-trip. Re-runs on already-stamped rows produce zero updates. Two ER workers stamping different sources whose fan-outs share referencers acquire locks in deterministic order — no deadlock setup.

When you actually want a hosted ER engine (not knot)

knot doesn't do ER. It exposes the SQL primitives a host needs to APPLY ER decisions atomically — stamping, FK fanout, cascade, idempotency. It does NOT score matches, run blocking strategies, calibrate probabilistic models, or train active-learning loops. That's policy; knot is the substrate underneath.

Reach for a hosted ER engine when ER quality itself is the differentiator and you'd rather buy than build the scoring logic: Senzing (deterministic + probabilistic engine, free dev tier, library-embeddable), Reltio / Tamr / Informatica (full MDM platforms — they bring scoring, golden record management, UI, steward workflows), Splink / Zingg / Dedupe (open-source ER libraries that ship the scoring without the substrate). Any of these can FEED knot — their match decisions become the assignments payload to binding.assign_canonicals_sql(). They're complementary, not competitive.

The re-ingest problem (solved)

Re-ingesting via write_sql's ON CONFLICT DO UPDATE preserves canonical_id + er_metadata but overwrites every other slot — including FK columns. ER's stamp guard (canonical_id IS NULL) then refuses to re-fanout (the rows are already stamped). The resolved view silently loses FK joins. knot ships binding.translate_fks_sql() as the recovery primitive. hitch's IngestWorkflow calls it after every upsert. 

-- One standalone UPDATE per FK slot (postgres planner reliably runs
-- standalone UPDATEs but can prune data-modifying CTEs sharing a
-- chain — we tested both shapes and found the prune; this is the safe form).
UPDATE hitch.movie_bindings AS b
SET director = m.canonical_id
FROM hitch.person_bindings AS m
WHERE b.source_name = 'imdb' AND m.source_name = 'imdb'
  AND m.canonical_id IS NOT NULL
  AND b.director = m.source_identifier;

Embeddings as a first-class slot type

types.VECTOR(384, metric="cosine") is just another slot type. DDL emits a vector(384) column AND an HNSW index with vector_cosine_ops. The query AST exposes slot.distance_to(target) that picks the pgvector operator from the slot's metric. The ER candidate-finding query is a one-line substrate primitive, not raw SQL.

find_er_candidates_sql — real emit
SELECT
  u.source_identifier,
  u.name AS identity_val,
  (
    SELECT b.canonical_id
    FROM hitch.person_bindings b
    WHERE b.canonical_id IS NOT NULL
      AND b.source_name <> 'imdb'
      AND b.name_embedding IS NOT NULL
      AND (b.name_embedding <=> u.name_embedding)
            < %(threshold)s
    ORDER BY b.name_embedding <=> u.name_embedding
    LIMIT 1
  ) AS match_canonical_id
FROM hitch.person_bindings u
WHERE u.source_name = 'imdb'
  AND u.canonical_id IS NULL
  AND u.name_embedding IS NOT NULL
  AND u.name IS NOT NULL
  AND length(trim(u.name::text)) > 0;

Operator picked from the slot's metric. <=> for cosine, <-> for l2, <#> for ip — matching the HNSW index knot built for the same slot.

When you actually want a vector DB (not knot's vector slots)

Pinecone, Weaviate, Qdrant, Milvus — purpose-built vector databases. Use them when vector similarity IS the workload: semantic search over millions-to-billions of documents, RAG retrieval at request time, recommendation systems where the vector query is the hot path. They specialize in vector ergonomics (filter + boost + rerank), they scale vector compute on dedicated hardware, and they ship operational tooling for the embedding lifecycle.

knot's vector slots are for the opposite case: vectors as one signal among many attached to entities you also model relationally. The embedding is a slot on the bindings table, alongside text and integer slots, with HNSW for the ER candidate-query path and the occasional k-NN. If your problem is "give me the 50 nearest items out of 10 million vectors at p99 < 50ms," you want Pinecone — knot will struggle past a few million rows on a single postgres.

Why knot deserves to exist

Adjacent tools are competent at their own job. PyPika builds SQL strings, jOOQ types them, SQLAlchemy Core declares schemas, LinkML compiles YAML to DDL, dbt orchestrates models, Splink does ER scoring, Neo4j stores graphs, RDF stores triples, Senzing resolves entities as a service. None combines typed schema-as-code authoring + postgres SQL compile target + multi-source bindings + weighted resolved view + ER cascade primitive + embeddings as a slot type into one library.

That combination is what every in-house MDM build keeps re-inventing — six load-bearing patterns that have to agree with each other or the system silently drifts. knot eliminates the drift by compiling them all from one spec.

The single fact that justifies knot

Change movie.col.year >= 1888 in the spec. That change shows up in: the validation SELECT, every virtual class predicate that referenced it, every query's .where() that filtered on it, the GraphQL SDL emitted from the spec, and the FK chain logic in the resolved view. One edit. Zero drift.

The single primitive nothing else has

binding.assign_canonicals_sql() — one atomic SQL statement that stamps canonical_ids, translates forward FKs, fans out backward references, and is strictly idempotent. Every production MDM team has built a buggier version of this.

The single posture that makes it work

knot is a substrate, not a runtime. No connections, no scheduler, no migration engine, no ER policy baked in. Your team keeps Atlas/sqldef for migrations, Temporal for orchestration, your existing ER policy, your existing auth. knot replaces only the compiler-shaped piece — and only that.

The reference deployment that proves it

hitch wires knot into Temporal + FastAPI + Ariadne + sentence-transformers + pgvector. 461 tests green, brings up with one docker compose up, reviewed by 5 hard-nosed personas — all five APPROVE_WITH_GAPS. Every substrate-side gap they found is landed.

Where it doesn't oversell

closed P0 — corrections weight silent failure
Forgetting to seed _user_corrections would silently lose every mutation. Closed via emit_weight_seed auto-seeding the corrections row at CORRECTIONS_DEFAULT_WEIGHT (1e6) regardless of caller defaults. Operator can still tune per (class, slot) — agency preserved.
closed ER fan-out lock-ordering deadlock
Workers stamping different sources whose fan-outs share referencers could acquire row locks in different orders. Closed: cls.referrers sorted alphabetically before emit.
closed Hand-rolled raw SQL in the ER activity
hitch's er_via_embeddings hand-rolled the k-NN candidate query as an f-string. Closed: new binding.find_er_candidates_sql() substrate primitive; activity calls it; operator picked from the slot's declared metric.
closed explain_winner_sql tie-break divergence
RANK() over weight only — labeled tied-weight rows both is_winner=true while the resolver picked one. Closed: ROW_NUMBER() with the resolver's exact tie-break tuple.
closed Embedding model drift unauditable
hitch's er_metadata now records model_name + embedding_dim on every stamped row. A backfill script can scan for stale models and re-decide.
closed back() redundant with this
Reverse-FK navigator renamed to via and re-typed to take an FkRef. Validation moves to the .col access; FK-target mismatch becomes a TypeError at the call site. One way to do everything.
open GraphQL N+1 → DataLoader
Per-request memoization halves roundtrips today. True batched IN-list DataLoader for distinct FK targets per request is the next step. Lives in knot_graphql.Resolvers.
open Resolved view scaling
Per-slot correlated subqueries scale ~25× more buffer hits than a window-function rewrite at 10M bindings. Plan: opt-in emit_resolved_view_window for production cardinality.
open ER needs_review bucket
Binary policy today: below threshold → match, above → mint. A distance-band needs-review bucket is the natural extension. Host-side policy add.
open DLQ + cursor durability in hitch
Ingest workflow discards validation-fail rows after counting them. fetch_seed_batch reads from disk — production needs cursor durability + rate-limited source APIs. Host concerns; knot doesn't change.
