The problem

You have a domain — let's say movies. Three sources publish data about it: imdb, tmdb, rottentomatoes.

They all describe the same things. They all disagree:

sourcetitleyearruntimedirector ref
imdbReservoir Dogs199299nm_qt
tmdbReservoir Dogs199299tmdb_138
rottentomatoesReservoir Dogs1992100rt_qt

Different runtime values. Different director IDs (each source's own namespace). Same movie.

What we need

  1. One schema that says "this is a Movie; here are its slots."
  2. Many sources publishing claims into that schema, each keeping their own row.
  3. One fused view per entity that picks per-slot winners by some weighting policy.
  4. Entity resolution that figures out which source-rows are the same real-world thing.
  5. Constraints that catch data-quality violations before they reach consumers.
  6. Some graph-ish querying — multi-hop FK walks, reverse references, correlated aggregates — but not a full graph DB.
  7. Embeddings as a signal for matching (and maybe search) — but not a primary vector DB.

What we're not building

not a graph DB

We have 5 known FK relationships, not 11,000 Wikidata properties. No variable-length path traversal. No open-set predicates. No OWL reasoning.

not a vector DB

Vectors are one signal attached to entities. Not millions-of-document RAG retrieval on the request path. pgvector inside postgres is enough.

not an ORM

No identity map, no unit of work, no auto-flushing dirty tracking. This is MDM, not OLTP CRUD against a single-source schema.

not an ER engine

We don't score matches or run blocking strategies. We apply ER decisions atomically. Splink / Senzing / Dedupe feed us, not compete with us.

Knowing what's out of scope is what lets the in-scope substrate stay small.

The split: substrate vs runtime

knot — the substrate

Typed Python compiler. Takes a multi-source MDM spec, emits postgres SQL.

  • DDL — tables + views + indexes
  • Read SQL — typed queries over the resolved view
  • Write SQL — upsert + ER cascade + retract templates
  • Constraint SQL — one SELECT per rule
  • Vector SQL — k-NN candidate selection

No connections. No scheduler. No HTTP. Pure library.

hitch — the reference runtime

What a real team would build around knot.

  • Temporal — ingest / embed / ER / validate workflows
  • FastAPI + Ariadne — GraphQL queries + mutations
  • sentence-transformers — real embeddings, not mocked
  • pgvector — HNSW indexes

Authoring: the spec

Schema-as-code, in typed Python. The spec IS the single source of truth.

from knot import Spec, types, this

spec = Spec(identifier_slot_name="canonical_id", schema="hitch")

person = spec.add_class("Person")
person.slot("name", types.TEXT, required=True)
person.slot("birth_year", types.INTEGER)
person.slot("name_embedding", types.VECTOR(384, metric="cosine"))

movie = spec.add_class("Movie")
movie.slot("title", types.TEXT, required=True)
movie.slot("year", types.INTEGER)
movie.slot("director", person)           # FK by passing the class
movie.slot("title_embedding", types.VECTOR(384, metric="cosine"))

for src in ("imdb", "tmdb", "rottentomatoes"):
    spec.add_source(src).bind(movie)     # multi-source = first class

Constraints — same vocabulary as queries

A constraint body is the same Expr AST you'd write in a query .where() clause. One vocabulary, three uses.

movie.add_constraint(
    "year_sane",
    body=movie.col.year >= 1888,           # cinema started here
)

movie.add_constraint(
    "movie_director_alive_at_release",     # FK-chain predicate
    body=movie.col.director.birth_year.is_null()
       | movie.col.year.is_null()
       | (movie.col.director.birth_year < movie.col.year),
)

Same expression composes in:

  • add_constraint(body=...) — validators
  • add_virtual(where=...) — virtual subclasses
  • cls.resolved.where(...) — runtime queries

Virtual classes

A predicate over the resolved view becomes a queryable subclass with its own GraphQL type:

movie.add_virtual("RecentMovie",
    where=movie.col.year >= 1995)

movie.add_virtual("ClassicMovie",
    where=movie.col.year.is_not_null() & (movie.col.year <= 1985))

movie.add_virtual("Blockbuster",
    where=movie.col.box_office_usd.is_not_null()
        & (movie.col.box_office_usd >= 100_000_000))

# Correlated — "movies that have at least one director credit"
movie.add_virtual("DirectedMovie",
    where=((credit.col.movie == this.Movie)
         & (credit.col.role == "director")).any())

Each emits a CREATE VIEW; GraphQL exposes recentMovieList, blockbusterList, etc.

What spec.ddl() emits

One canonical CREATE script per spec. Idempotent (CREATE IF NOT EXISTS / CREATE OR REPLACE).

Per concrete class
  • <cls>_bindings table
  • <cls>_resolved view
  • <cls>_all_sources view
  • btree on canonical_id
  • HNSW per Vector slot
Per virtual class
  • <virtual> view filtering the concrete root's resolved view
Global
  • source_weight table
  • CREATE EXTENSION vector (if any VECTOR slot)
  • CREATE SCHEMA

For the hitch demo (4 concrete + 6 virtual classes): ~20 KB of SQL, deploys in <100ms.

Multi-source fusion — three relations

This is the core of knot. Every concrete class compiles to:

1. bindings table

One row per (source, source_id). Every source's raw claim plus the ER-stamped canonical_id.

PK on (source_name, source_identifier)
2. resolved view

One row per canonical_id. Each slot is the highest-weight non-NULL claim across sources.

The "current state" view
3. all_sources view

One row per canonical_id. Each slot is a jsonb_object_agg mapping source → {value, weight}.

The provenance / audit surface

Plus a fourth global table — source_weight — that holds the per-(source, class, slot) weight policy. Runtime-mutable.

resolved view — per-slot argmax

Each slot is a correlated subquery: highest weight wins, NULL skip, alphabetical tie-break.

CREATE VIEW hitch.movie_resolved AS
SELECT
  cb.canonical_id,
  (SELECT b.runtime_minutes
   FROM hitch.movie_bindings b
   LEFT JOIN hitch.source_weight w
     ON w.source_name = b.source_name
    AND w.class_name = 'Movie'
    AND w.slot_name  = 'runtime_minutes'
   WHERE b.canonical_id = cb.canonical_id
     AND b.runtime_minutes IS NOT NULL   -- ← NULL-skip
   ORDER BY COALESCE(w.weight, 0) DESC,   -- ← argmax
            b.source_name                 -- ← alphabetical tie-break
   LIMIT 1) AS runtime_minutes,
  -- … one correlated subquery per slot …
FROM (SELECT DISTINCT canonical_id FROM hitch.movie_bindings
      WHERE canonical_id IS NOT NULL) cb;

NULL-skip is by design

A high-weight source that has NULL loses to a lower-weight source that has a value:

If rt had a value of 175, it would still lose (weight 0.50 < 0.85). But because rt has no claim, argmax doesn't consider it at all. Resolved value: 170.

NULL ≠ "the value is NULL." NULL = "no claim made."

One row per canonical_id. Each slot is a jsonb mapping source → {value, weight}.

{

  "runtime_minutes": {
    "imdb":           {"value": 99,  "weight": 0.85},
    "tmdb":           {"value": 99,  "weight": 0.70},
    "rottentomatoes": {"value": 100, "weight": 0.50}
  },
  "title": {
    "imdb":           {"value": "Reservoir Dogs", "weight": 0.85},

The audit surface — "why did the resolver pick X?" Every source's claim is here.

source_weight — runtime policy

One row per (source_name, class_name, slot_name, weight). Auto-seeded by emit_weight_seed(); operator-tunable per (class, slot) at runtime.

source_nameclass_nameslot_nameweight
imdbMovieruntime_minutes0.85
tmdbMovieruntime_minutes0.70

The _user_corrections row is auto-seeded at 1e6 regardless of caller defaults — closes the silent-failure window where forgetting to seed corrections would lose every mutation. Operators can still tune per (class, slot).

_user_corrections — the designated override surface

knot auto-creates a synthetic source on every spec, auto-bound to every concrete class. Its weight dominates the argmax. A correction is just a binding row.

mutation {
  correctMovie(
    canonical_id: "m_bd6c1bef…",
    source_identifier: "ops-fix-2026-05-23",
    runtime_minutes: 100         # override the imdb winner
  ) {
    runtime_minutes              # returns 100 — corrections dominates
  }
}

bindings table after the write:

imdb 99 weight 0.85
tmdb 99 weight 0.70
rt 100 weight 0.50
_user_corrections 100 weight 1e6 ← argmax winner

Retract via mutation { retract(...) } → the corrections row deletes → original argmax restores.

explain_winner_sql — per-slot diagnostic

"Why did slot X resolve to value Y?" — one row per (canonical_id, source) with is_winner + margin.

margin = winner.weight − runner_up.weight. NULL if no runner-up (more honest than 0, which reads as "tied with second").

Uses ROW_NUMBER() OVER (ORDER BY weight DESC, source_name) — same tie-break as the resolver, so the diagnostic can't lie.

Queries — three shapes, one builder

Relational filters, FK chain walks, vector k-NN. They compose in the same Query AST.

# 1. Relational filter on the resolved view
movie.resolved.where(movie.col.year >= 1995).select(movie.col.title)

# 2. Multi-hop FK chain — attribute access
(movie.resolved
  .where(movie.col.director.birth_year < movie.col.year)
  .select(movie.col.title, movie.col.director.name))

# 3. k-NN over a vector slot
(movie.from_source(imdb)
  .order_by(movie.col.title_embedding.distance_to(target_vec))
  .limit(10))

Each compiles to one SQL string. The host runs it.

FK chains → auto LEFT JOIN

This Python:

(movie.resolved
  .where(movie.col.director.birth_year < movie.col.year)
  .select(movie.col.title, movie.col.director.name))

compiles to:

SELECT m.title, movie_director.name
FROM hitch.movie_resolved m
LEFT JOIN hitch.person_resolved AS movie_director
  ON movie_director.canonical_id = m.director
WHERE movie_director.birth_year < m.year;

The JOIN alias (movie_director) is deterministic — two FKs to the same target get distinct aliases. The compiler walks the AST, collects FK chains, emits JOINs once.

Reverse navigation — cls.via(other.col.fk)

FKs are directional (the column lives on one side). knot exposes the inbound side as a typed FkRef navigator:

# "directors with more than one director credit"
(person.resolved
  .where(person.via(credit.col.person)
                .where(credit.col.role == "director")
                .count() > 1)
  .select(person.col.name))

compiles to:

SELECT person_resolved.name
FROM hitch.person_resolved
WHERE (SELECT COUNT(*) FROM hitch.credit_resolved
       WHERE credit_resolved.person = person_resolved.canonical_id
         AND credit_resolved.role = 'director') > 1;

The typed FkRef arg means typos raise at credit.col.persn (one step earlier than the via call); mismatched FK targets raise at via() itself.

Graph engines get bidirectional traversal for free (edges are first-class). SQL FKs are columnar — knot closes the everyday gap with the same correlated-subquery shape you'd write by hand.

Three materializers — .count() / .any() / .none()

# How many director credits does each person have?
person.via(credit.col.person).where(credit.col.role == "director").count()

# Does this person have ANY actor credit?
person.via(credit.col.person).where(credit.col.role == "actor").any()

# Has this person NEVER acted?
person.via(credit.col.person).where(credit.col.role == "actor").none()

All three compile to correlated subqueries:

-- .count()  →  (SELECT COUNT(*) FROM credit_resolved WHERE …)
-- .any()    →  EXISTS    (SELECT 1     FROM credit_resolved WHERE …)
-- .none()   →  NOT EXISTS(SELECT 1     FROM credit_resolved WHERE …)

Entity resolution — one atomic statement

Most MDM stacks orchestrate ER as multiple steps. knot ships it as one writable-CTE chain:

  1. Stamp — assign canonical_id to unstamped binding rows of (source, class)
  2. Forward FK translation — rewrite this row's FK columns from source-id → canonical-id
  3. Backward fan-out — for each referencing class, rewrite ITS FK column where it held this row's source-id
  4. Register — implicit; canonical_id is now in the bindings table

Strictly idempotent. Re-runs on already-stamped rows produce zero updates. Two ER workers stamping different sources acquire locks in deterministic order — no deadlock.

binding.assign_canonicals_sql() — the chain

WITH stamp AS (
  UPDATE hitch.person_bindings AS b
  SET canonical_id = a.canonical_id,
      er_metadata  = COALESCE(a.er_metadata, b.er_metadata)
  FROM jsonb_to_recordset(%(assignments)s::jsonb)
       AS a(canonical_id text, source_identifier text, er_metadata jsonb)
  WHERE b.source_name = 'imdb'
    AND b.source_identifier = a.source_identifier
    AND b.canonical_id IS NULL          -- idempotency guard
  RETURNING b.canonical_id, b.source_identifier
),
fanout_credit AS (                       -- backward fan-out
  UPDATE hitch.credit_bindings AS r
  SET person = COALESCE(
    (SELECT canonical_id FROM stamp WHERE source_identifier = r.person),
    r.person)
  WHERE r.source_name = 'imdb'
    AND EXISTS (SELECT 1 FROM stamp WHERE source_identifier = r.person)
),
fanout_movie AS ( -- … same shape for every referencing class … )
SELECT 1;

The re-ingest problem — and the recovery primitive

Re-ingesting via write_sql's ON CONFLICT DO UPDATE preserves canonical_id and er_metadata, but overwrites every other slot — including FK columns. ER's stamp guard (canonical_id IS NULL) then refuses to re-fanout.

Resolved view silently loses FK joins. knot ships binding.translate_fks_sql() as the recovery primitive — hitch's IngestWorkflow calls it after every upsert.

UPDATE hitch.movie_bindings AS b
SET director = m.canonical_id
FROM hitch.person_bindings AS m
WHERE b.source_name = 'imdb' AND m.source_name = 'imdb'
  AND m.canonical_id IS NOT NULL
  AND b.director = m.source_identifier;

One standalone UPDATE per FK slot (CTE chains can get planner-pruned in this shape; standalone UPDATEs are reliable).

Embeddings — first-class slot type

types.VECTOR(384, metric="cosine") is just another slot. DDL emits a vector(384) column AND an HNSW index with vector_cosine_ops.

person.slot("name_embedding", types.VECTOR(384, metric="cosine"))
movie.slot("title_embedding", types.VECTOR(384, metric="cosine"))

# k-NN composes anywhere a value expression does
q = (movie.from_source(imdb)
     .order_by(movie.col.title_embedding.distance_to(target_vec))
     .limit(10))

# Distance picks the pgvector operator from the slot's metric:
#   cosine → <=>     l2 → <->     ip → <#>
# matching the HNSW index built for the same slot

find_er_candidates_sql — the ER substrate primitive

Per unresolved binding in (source, class), the nearest stamped neighbor in OTHER sources within %(threshold)s:

sql = binding.find_er_candidates_sql(
    identity_slot="name",           # KeyError on typo
    embedding_slot="name_embedding", # TypeError if not Vector
)
# host binds %(threshold)s; results: (source_identifier, identity_val,
# match_canonical_id NULL if no neighbor within threshold)
for c in execute(sql, {"threshold": 0.35}):
    cid = c["match_canonical_id"] or mint_fresh(c["identity_val"])
    decisions.append({"canonical_id": cid,
                      "source_identifier": c["source_identifier"]})
binding.assign_canonicals_sql() # ← apply atomically

Knot owns the mechanics (slot, op, source-scope). Host owns the policy (threshold, mint fallback, needs-review band).

Every DB write goes through a knot SQL emitter. Workflow code never imports knot directly — only activities do (per the replay-safety contract).

Temporal workflows in hitch

IngestWorkflow (per source, class)

fetch → validate → bucket → upsert → translate_fks

EmbedWorkflow (per source, class, vector slot)

fetch unembedded → sentence-transformers → write embedding

ERWorkflow (per class)

per source: find_er_candidates → decide (k-NN match or sha1 mint) → assign_canonicals

ValidationSweepWorkflow

run every spec.emit_validation() SELECT; report per-rule counts

Replay safety: workflows never import knot's emitters. Compiling a SQL string is deterministic but leaks the spec module ref into the workflow history — a redeploy with a different spec replays into poisoned state. Activities own all SQL emission.

One spec edit. Zero drift.

Change movie.col.year >= 1888 in the spec. It shows up in:

  • the validation SELECT
  • every virtual class predicate that referenced it
  • every query's .where() that filtered on it
  • the GraphQL SDL emitted from the spec
  • the FK chain logic in the resolved view

This is the single fact that justifies knot.

No tool in the comparison landscape (SQLAlchemy / jOOQ / LinkML / dbt / Drizzle / Ecto / Diesel) gives you all five from one spec. They give you one or two; the other three drift.

Where knot sits

peers (same style)

SQLAlchemy Core, Ecto, Drizzle, Diesel — typed combinator DSLs over relational data.

knot adds: the MDM domain layer above tables.

consumers

Splink, Senzing, Dedupe, Zingg — ER engines. Their match decisions feed binding.assign_canonicals_sql().

Complementary, not competitive.

alternatives (different shape)

Reltio / Tamr / Informatica — buy-vs-build. Neo4j / RDF — graph DBs. Pinecone — vector DBs.

Out of category.

After looking hard: no direct competitor on the combined surface (typed spec + postgres compile + multi-source bindings + weighted resolved view + ER cascade primitive + embeddings).

What knot is NOT — recap

not a graph DB

Closed-set FK relations. Use Neo4j/RDF for open topology + variable-length paths.

not a vector DB

Vectors as ONE signal. Use Pinecone/Weaviate when similarity IS the workload.

not an ORM

No identity map, no auto-flushing. Use SQLAlchemy ORM for OLTP CRUD.

not an ER engine

We APPLY ER, we don't SCORE. Use Splink/Senzing for matching policy.

Honest scope-fences make the substrate convincing, not weak. Knowing what's out of scope is what keeps the in-scope substrate small enough to trust.
