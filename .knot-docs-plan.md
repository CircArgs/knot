# knot docs plan

A fresh docs site at `docs/` (URL paths under `docs/content/`) that takes a reader who's never seen knot from "what is this?" to "I can confidently use every surface."

The site has six sections: **Overview**, **Tutorial**, **Spec model (the metaschema)**, **Compilation (postgres + GraphQL)**, **Data plane (db + graph)**, **API surface (REST + GraphQL)**, **Operating concerns**, **Reference**. About 40 pages total. Static markdown for reference + concepts; runnable marimo notebooks for end-to-end stories, iterative spec edits, GraphQL exploration, and ingest-then-query flows.

The audience is a developer or operator who has never seen knot. Don't assume LinkML / Splink / dbt / Marquez familiarity — link out when those help, but always introduce knot's primitives in knot's own terms.

## Per-page brief

### 1. `index.md` — Overview & first 60 seconds  (static)
- **What:** A landing page that says what knot is in two sentences (knowledge-graph + ontology platform; postgres data plane; API-first), shows the smallest possible end-to-end ingest in ~15 lines, and routes the reader to the right section.
- **Why separate:** It's the front door. It must be skimmable in under a minute and not leak architecture vocabulary that hasn't been introduced yet.
- **How to teach:** Three callouts ("Build a spec, push rows, query knot"), a code block lifted from the start of `notebooks/02_end_to_end_story.py`, links to the tutorial section. References: `knot/__init__.py`, `knot/api/main.py`. Static markdown.

### 2. `why-knot.md` — Why knot exists, what it isn't  (static)
- **What:** Position knot against neighbors a reader might assume it copies (LinkML, dbt, DataJunction, Splink, Atlas, Marquez). Three positive claims (single-team trust posture; spec graph is reflective; query-time trust resolution), and a list of explicit non-goals (no scheduler, no internal SQL engine, no multi-tenant defenses).
- **Why separate:** Readers anchored on those tools will misread knot's posture without an explicit position statement. Keeping non-goals out of `index.md` keeps the front door positive.
- **How to teach:** Comparison table; one paragraph per non-goal with the reason it's not a deferral but a commitment. References: `CLAUDE.md` "Posture" section. Static markdown.

### 3. `architecture-at-a-glance.md` — The seven boxes diagram  (static)
- **What:** One picture of the runtime: spec store, graph store, extensions dispatcher, REST router, GraphQL endpoint, lake materialization, DQ. Arrows show what calls what; postgres sits behind everything.
- **Why separate:** Every later section assumes the reader has this mental map. A single page that the reader can flip back to.
- **How to teach:** SVG/mermaid diagram + a legend that maps each box to its module path. References: `knot/api/main.py` for the wiring, `knot/db/__init__.py` for the persistence cut, `knot/spec/compile/` for compilation. Static markdown.

### 4. `glossary.md` — Vocabulary  (static)
- **What:** Definitions for every load-bearing term: spec, source, canonical_id, knot_row_id, binding, contribution, draft, revision, content hash, polymorphic class, defined class, derived slot, trust posterior, correction, lineage, tombstone.
- **Why separate:** The metaschema page (#12) shouldn't double as a dictionary; readers will Cmd-F here when a later page uses a term they forgot.
- **How to teach:** Alphabetical, one sentence + a one-line example per term. Cross-link to the page where each term is taught in depth. Static markdown.

### 5. `tutorial/01-spec-up-to-publish.py` — Author a spec from zero  (marimo)
- **What:** Walk from an empty postgres to a published Movie spec. Drives `/spec/drafts`, `/spec/drafts/{id}/types`, `/slots`, `/classes`, `/sources`, `/publish` exactly as `notebooks/01_initial_spec_and_sources.py` does today, with extra prose between cells.
- **Why separate:** First contact with knot. Kept short — only the spec, no data.
- **How to teach:** Adapt `notebooks/01_initial_spec_and_sources.py`. Show the published-summary endpoints (`/spec/published/classes`, etc.) at the bottom so the reader sees the result.  Marimo notebook (live REST calls; reader must have the dev stack up).

### 6. `tutorial/02-ingest-multi-source.py` — Two sources disagree  (marimo)
- **What:** Add a second source, ingest disagreeing rows, observe the multi-row contributions for the same canonical_id, see the resolved view's tiebreak under uniform priors.
- **Why separate:** This is the "aha" — knot doesn't pick a winner at write time. Showing this without yet introducing corrections keeps the lesson focused.
- **How to teach:** Lift cells 4-5 of `notebooks/02_end_to_end_story.py`. References: `api/graph/ingest.py`, `api/graph/reads.py`, `graph/resolve.py`. Marimo.

### 7. `tutorial/03-correct-and-learn.py` — Corrections drive bandit feedback  (marimo)
- **What:** Submit a `PropertyCorrection`, watch the audit row, the synthetic `_user_corrections` row, and the per-(source, slot) Beta posteriors update. Re-resolve; the answer flips. End with the audit walk-back.
- **Why separate:** The closed loop (correction → posterior → resolution) is the design's most distinctive idea. It earns its own notebook.
- **How to teach:** Lift cells 6-8 of `notebooks/02_end_to_end_story.py` plus prose. References: `api/graph/corrections.py`, `graph/corrections.py`, `db/trust_posteriors.py`, `graph/resolve.py`. Marimo.

### 8. `tutorial/04-relations-and-constraints.py` — Relations, derivations, constraints  (marimo)
- **What:** Add a `Person` and `Credit` class. Define `Movie.credit_count` as a `RelationCount`-derived slot. Add a `Constraint` ("every movie must have at least one credit") via the JSON-expression body translator. Try ingesting a movie that violates it; see the 422.
- **Why separate:** The metaschema's expressive power isn't visible from the Movie-only flow. This page is the proving ground for derived slots, RelationAll/RelationAny, and `validate_constraints=true`.
- **How to teach:** New notebook. References: `spec/metaschema.py` expression tree, `api/constraint_translator.py`, `spec/compile/postgres/_relation.py`, `api/graph/ingest.py`'s constraint-validation path. Marimo.

### 9. `tutorial/05-graphql-exploration.py` — GraphQL surface  (marimo)
- **What:** Open `/graph/query`, run `movies(where: {year: {gt: 1990}})`, then `movieByCanonicalId`, then `movieResolved`, then `movieAggregate`. Show derived-slot WHERE/ORDER BY. End with a `byDiscriminator` query against a polymorphic class.
- **Why separate:** GraphQL is a surface, not a primitive. It deserves its own walk so readers learn the query patterns without having to read `spec/compile/graphql/__init__.py`.
- **How to teach:** New notebook with embedded GraphiQL screenshots and copy-pasteable queries. References: `spec/compile/graphql/__init__.py`, `api/graph/graphql.py`. Marimo.

### 10. `tutorial/06-rollback-and-history.py` — Spec lifecycle in time  (marimo)
- **What:** Create three drafts/revisions. Show `/spec/revisions`. Run `/spec/rollback/{n}`. Show `as_of=N` on graph reads pinning to a prior revision. Show that rollback applies the destructive-change gate.
- **Why separate:** Time travel + rollback aren't part of the simple-flow narrative; readers operating knot in production need this.
- **How to teach:** New notebook. References: `db/spec_store.py` (revisions, publish_draft), `api/spec.py` (rollback endpoint). Marimo.

### 11. `spec/overview.md` — The spec graph, 30k feet  (static)
- **What:** A spec is a typed Pydantic graph of `OntologyClass`, `Slot`, `TypeDefinition`, `Source`, `Constraint` connected by *real Python references* (commitment 2). Names live only at the persistence boundary.
- **Why separate:** Sets the framing for every detail page (#12-#20). Without it, those pages read as random catalog entries.
- **How to teach:** Annotated diagram of a tiny spec (Movie + imdb_id + Source). Walk the in-memory shape vs. the JSONB shape. References: `knot/spec/__init__.py`, `knot/spec/metaschema.py` (top-of-file docstring). Static markdown.

### 12. `spec/classes-slots-types.md` — The structural primitives  (static)
- **What:** `OntologyClass` (concrete vs abstract vs defined), `Slot` (range, identifier, required, multivalued, resolution_policy), `TypeDefinition` (primitive base + pattern), `SlotOverride`, `UniqueKey`, `PermissibleValue`. The class chain (`is_a`, mixins).
- **Why separate:** This is the "core schema vocabulary" page. Detail-rich; cross-linked from many other pages.
- **How to teach:** One subsection per type with a minimal Python literal + the JSONB it serializes to. References: `knot/spec/metaschema.py` lines 134-660; the `_class_chain()` walk; `knot/db/_naming.py:effective_slots`. Static markdown.

### 13. `spec/expression-tree.md` — The unified expression substrate  (static)
- **What:** One expression-tree language used in derivations, constraint bodies, defined-class definitions, and SDK-built predicates. Catalog: `Literal_`, `SlotPath`, `Compare` + `_BoolComposable`, `BoolExpr`, `Within`, `Between`, `Matches`, `RelationRef`, `FilteredRelation`, `RelationProject`, `RelationCount`, `RelationAggregate`, `RelationAny`, `RelationAll`, `RelationFirst`, `ReverseRelation`, `RecursiveTraversal`, `ScalarDerivation`, `FormatDerivation`.
- **Why separate:** It's the most reused substrate in the codebase; teaching it once unlocks derivation, constraints, GraphQL `where`, and class definitions.
- **How to teach:** Each node with a one-liner and a Python-SDK example (`Movie.year > 1900`, `Movie.credits.where(role="director")`). Show the postgres SQL each compiles to. References: `knot/spec/metaschema.py` lines 154-376, `knot/spec/compile/postgres/_predicate.py`, `_relation.py`. Static markdown.

### 14. `spec/derivation.md` — Slot.derivation, query-time projections  (static)
- **What:** Derived slots have `derivation` set instead of being stored. They aren't columns; they're correlated subqueries appended to the SELECT list.
- **Why separate:** Readers commonly assume derivations are materialized; the "projection at query time" model is load-bearing for understanding why publish doesn't need to backfill.
- **How to teach:** One concrete example (`Movie.credit_count` from a `RelationCount`). Show: the spec literal, the JSON `derivation:` body in `POST /spec/drafts/.../slots`, the SQL that lands in `_queries.derived_column_exprs`. References: `knot/spec/metaschema.py:Slot.derivation`, `knot/spec/compile/postgres/_queries.py:select_with_derivations`, `knot/spec/compile/postgres/_relation.py`. Static markdown.

### 15. `spec/constraints.md` — Validation invariants  (static)
- **What:** A `Constraint` has `primary` (the class), `body` (an expression-tree node), `severity` (ERROR or WARNING), and `message`. Constraints compile to a SELECT in the uniform shape `(rule_id, class_name, slot_name, offending_pk, detail)`.
- **Why separate:** Constraints touch the publish gate, the ingest pre-commit check, and the `/graph/constraints/check` endpoint. One page so all those paths share one definition.
- **How to teach:** Walk one constraint end-to-end ("title must not be empty"). Show the JSON body, the metaschema tree, the compiled SQL, and what `validate_constraints=true` does on ingest. References: `knot/spec/metaschema.py:Constraint`, `knot/spec/compile/postgres/__init__.py:compile_constraint`, `knot/api/graph/constraints.py`, `knot/api/graph/ingest.py`. Static markdown.

### 16. `spec/references-and-polymorphism.md` — How classes refer to each other  (static)
- **What:** `DirectRef` (plain FK), `DiscriminatedRef` (class_slot + key_slot — polymorphic ref), `IdentifierPattern` (class-level: this class IS polymorphic). Why polymorphic classes can't be the target of a `Source`.
- **Why separate:** Polymorphism is the design's biggest single source of confusion; it gets a focused page rather than being a subsection of #12.
- **How to teach:** Two complete examples — a Movie with a `director: Person` (DirectRef) and an `Identifier` polymorphic class with `(class_slot=imdb_id, key_slot=value)`. Explain the publish-gate rule that rejects Source-on-polymorphic-class. References: `knot/spec/metaschema.py:DirectRef, DiscriminatedRef, IdentifierPattern`, `knot/db/spec_store.py:publish_gate` (the polymorphic-source check). Static markdown.

### 17. `spec/mixins-and-defined-classes.md` — Trait composition & equivalentClass  (static)
- **What:** Mixins are pure trait composition — their slots land on every including class's own table; collisions fail the publish gate. Defined classes (`is_a` + `definition`) compile to a postgres VIEW over the parent class's table.
- **Why separate:** Two distinct features that are easy to confuse but solve very different problems. One page sets them side-by-side.
- **How to teach:** "Director ≡ Person ⊓ ∃Credit.role='director'" as the canonical defined-class example. A `Timestamped` mixin (created_at, updated_at) as the canonical mixin example. Show the diff: defined classes drop+add VIEW DDL; mixins drop+add columns. References: `knot/db/_naming.py:effective_slots`, `knot/db/spec_store.py:_detect_mixin_cycle, _detect_mixin_slot_collision`, `knot/spec/compile/postgres/migration.py:AddDefinedClass`. Static markdown.

### 18. `spec/sources.md` — Where rows enter knot  (static)
- **What:** A `Source` declares (name, entity_class, identifier_slot). Knot starts at "normalize" — extraction/transformation happen upstream. Polymorphic classes can't be sourced; user-correction rows go through the synthetic `_user_corrections` source.
- **Why separate:** Sources sit at the boundary between knot and the outside world. Reads of `/graph/ingest/{source}` need a clean place to land.
- **How to teach:** Show the full lifecycle of one row: `imdb_id="tt0111161"` enters via `/graph/ingest/imdb`, lands as `(_source='imdb', _source_row_id='tt0111161', ...)` in `knot_data.movie`, opens an initial binding. References: `knot/spec/metaschema.py:Source`, `knot/api/graph/ingest.py`, `knot/db/graph_store.py:insert_rows`, `knot/db/_naming.py:user_corrections_source`. Static markdown.

### 19. `spec/sdk-affordances.md` — How `Movie.year > 1900` works  (static)
- **What:** `Slot.__gt__` and friends return `Compare` nodes; `Slot.from_source(s).is_null()`, `Slot.within([…])`, `Slot.between(a, b)`, `Slot.matches(pattern)`, `Slot.starts_with(...)`. `OntologyClass.__getattr__` walks the class chain. `_BoolComposable` mixin gives `&`, `|`, `~`.
- **Why separate:** The SDK is the friendly face of the expression tree; readers will recognize it from the tutorial but not understand how it's wired without this page.
- **How to teach:** Side-by-side: SDK syntax → expression-tree node → emitted SQL. References: `knot/spec/metaschema.py:_BoolComposable, Slot, OntologyClass.__getattr__`. Static markdown.

### 20. `spec/canonical-hashing.md` — Content hashing for revisions  (static)
- **What:** `canonical_dump` walks the spec graph, strips RUNTIME fields (descriptions, authoring metadata), strips defaults, and emits RFC 8785 JCS bytes. `compute_content_hash` is `sha256` of those bytes. Why named entities get `$ref` cycle handling and unnamed nodes (expression-tree) inline every time.
- **Why separate:** The content hash is referenced by spec_revisions, lake materialization, and GraphQL schema caching. One page so all those references share one definition.
- **How to teach:** Show the same spec authored two ways and confirm the hash is identical; show that adding a description doesn't change it; show that `tests/spec/test_canonical.py`'s pinned hash forces deliberate version bumps. References: `knot/spec/canonical.py`, the pin-hash test from `tests/`. Static markdown.

### 21. `compile/overview.md` — The two compilers  (static)
- **What:** knot is a compiler. The spec graph compiles to two surfaces: postgres DDL+queries (for the data plane) and a GraphQL schema (for the read API). Both compilers are pure: spec in, artifacts out.
- **Why separate:** Frames the four compile-detail pages so they read as two halves of the same idea.
- **How to teach:** Two-column diagram (spec → postgres / spec → GraphQL). Note that postgres is the only execution dialect today — GraphQL resolvers translate to postgres compiler calls. References: `knot/spec/compile/__init__.py` (one-line module header), `knot/spec/compile/postgres/`, `knot/spec/compile/graphql/`. Static markdown.

### 22. `compile/postgres-ddl.md` — Schema migration emission  (static)
- **What:** `diff_specs(prev, candidate)` returns typed `Change` dataclasses (`AddClass`, `DropClass`, `AddSlot`, `DropSlot`, `ChangeSlotType`, `AddDefinedClass`, `DropDefinedClass`, `ChangeSlotRequired`). `emit_ddl` is single-dispatch over them. `apply_changes` orders drops before adds. Destructive changes (DropClass / DropSlot / ChangeSlotType / DropDefinedClass) are gated by `allow_destructive`.
- **Why separate:** Migration is its own engine; readers operating knot need to know exactly what publish does to their database.
- **How to teach:** Step through `notebooks/02` line-by-line for "what DDL ran when I called `/publish`". Show the DDL for a defined class (CREATE OR REPLACE VIEW). References: `knot/spec/compile/postgres/migration.py`, `knot/db/spec_store.py:publish_draft` (the orchestration). Static markdown.

### 23. `compile/postgres-predicates.md` — singledispatch + `psycopg.sql.Identifier`  (static)
- **What:** Every expression-tree node has one handler registered against `compile_predicate`. `Literal_` pushes a placeholder; `SlotPath` emits an identifier; `Compare`/`BoolExpr`/`Within`/`Between`/`Matches` compose. `CompileContext` accumulates params and JOINs.
- **Why separate:** This is the architectural pattern (commitment: walk the typed entity tree). It's small enough to teach in one page; teaching it well prevents readers from inventing parallel approaches.
- **How to teach:** Walk one predicate end-to-end (`Movie.year > 1900` → SQL fragment + params list). Show the `_BINARY_OP_SQL` table; show the unary IS_NULL path. References: `knot/spec/compile/postgres/_dispatch.py`, `_predicate.py`, `_context.py`. Static markdown.

### 24. `compile/postgres-queries.md` — SELECT/JOIN/derived columns  (static)
- **What:** `select_with_binding(cls)` joins `knot_data.<cls>` × `knot_data.<cls>_bindings WHERE valid_to IS NULL`. `derived_column_exprs(cls)` adds correlated subqueries for derived slots. Defined classes go through their VIEW directly.
- **Why separate:** This is the read path's anchor. graph_store / GraphQL / DQ all start here.
- **How to teach:** One example with both stored + derived slots. Show the `(SELECT array_agg(...) FROM ...) AS credits` shape. Explain why derived params come *before* WHERE params in positional binding. References: `knot/spec/compile/postgres/_queries.py`, `knot/db/graph_store.py:query_rows`. Static markdown.

### 25. `compile/postgres-types.md` — range → column type  (static)
- **What:** `slot_pg_type(slot)` is a whitelist: `str→TEXT, int→BIGINT, float→DOUBLE PRECISION, bool→BOOLEAN, datetime→TIMESTAMPTZ, date→DATE`. Multivalued → `T[]`. OntologyClass-ranged slots → `TEXT` (canonical_id FK).
- **Why separate:** It's a small file but readers reach for it constantly when modeling. Standalone page = easy bookmark.
- **How to teach:** One table. Mention that user-supplied `slot.range.base` is *never* spliced raw into DDL — only the whitelist is honored. References: `knot/spec/compile/postgres/_types.py`. Static markdown.

### 26. `compile/lake-materialization.md` — Lake SELECT bodies  (static)
- **What:** `materialize_current(cls)` and `materialize_history(cls)` emit SELECT bodies (no DDL) — the operator wraps them in their target dialect (Trino CTAS, dbt, Iceberg MERGE INTO, etc.). Defined classes and abstract classes are skipped.
- **Why separate:** Lake materialization is an operator-facing artifact, not part of the request-time data plane.
- **How to teach:** Show the two SELECT bodies for a Movie class, then three example wrappers (Trino, dbt, Iceberg). Stress that knot does *not* execute these. References: `knot/spec/compile/postgres/lake.py`, `knot/api/lake.py`. Static markdown.

### 27. `compile/graphql-schema.md` — Dynamic Strawberry schema  (static)
- **What:** Per published Spec, build per-class `Type_Movie`, `WhereInput_Movie`, `OrderBy_Movie`, `AggregateResult_Movie`, plus the four/three resolvers (`movies`, `moviesCount`, `movieByCanonicalId`, `movieResolved`, `movieAggregate`; `…ByDiscriminator` for polymorphic). Schema cached by content_hash; rebuilds only on spec change. Resolvers delegate to graph_store/resolve — all SQL stays in db/.
- **Why separate:** GraphQL is the most complex compiler; it earns deep treatment without bloating the postgres pages.
- **How to teach:** Show the generated Strawberry source for a Movie spec (lifted via reflection). Walk one resolver from GraphQL request → `_build_pred` → `graph_store.query_rows` → result. Note the `exec()`-built resolvers and why they exist (per-class type bindings). References: `knot/spec/compile/graphql/__init__.py`, `knot/api/graph/graphql.py`. Static markdown.

### 28. `data/storage-shape.md` — How rows live in postgres  (static)
- **What:** Per concrete class: `knot_data.<class>` (source rows) + `knot_data.<class>_bindings` (SCD2). System columns (`_knot_row_id`, `_source`, `_source_row_id`, `_spec_revision`, `_ingest_at`). Bindings columns (`canonical_id`, `valid_from`, `valid_to`, `change_type`, `applied_revision`, `correction_id`). Partial indexes for the "current binding by canonical_id" hot path and for "exactly one current binding per knot_row_id."
- **Why separate:** This is *the* page operators come back to most. Storage shape is the contract every read/write conforms to.
- **How to teach:** One ER diagram with the two tables and the two indexes. Walk an INSERT then a Merge then a Tombstone showing the binding rows that result. References: `knot/db/control_schema.sql`, `knot/spec/compile/postgres/migration.py`, `knot/db/graph_store.py`. Static markdown.

### 29. `data/spec-store.md` — Drafts, revisions, publish gate  (static)
- **What:** `spec_revisions` is the immortal audit chain (published rows are never deleted). `create_draft` branches from a parent. `edit_draft` is a row-locked atomic R-M-W (the concurrency-safe primitive). The publish gate runs Pydantic shape recheck, reference resolution, mixin cycle/collision detection, defined-class compile check, and (in the publish path) post-INSERT constraint validation against existing data.
- **Why separate:** Spec lifecycle and concurrency safety belong together.
- **How to teach:** Step through `publish_draft` end-to-end, including the destructive-change classification and the `applied_revision` plumbing. References: `knot/db/spec_store.py:publish_gate, edit_draft, publish_draft`. Static markdown.

### 30. `data/graph-store.md` — Per-class CRUD primitives  (static)
- **What:** `insert_rows`, `query_rows`, `count_rows`, `aggregate_rows`, `get_canonical_contributions`, `merge_canonical_ids`, `split_canonical_id`, `insert_synthetic_row`, `tombstone_canonical_id`, `reject_contribution`, `upsert_user_correction_row`, `append_lineage_event`. Concurrency: every mutation that closes-then-opens bindings uses `SELECT FOR UPDATE`.
- **Why separate:** It's the persistence boundary; orchestration calls into here. Cleanly separated from #31 (orchestration).
- **How to teach:** One subsection per primitive: signature, what it touches, a tiny `psycopg` snippet showing the bindings before/after. References: `knot/db/graph_store.py`. Static markdown.

### 31. `data/corrections-orchestration.md` — Three things atomically  (static)
- **What:** `knot/graph/corrections.py` composes db primitives. Each correction wraps in one transaction: audit row, data-plane mutation, lineage event (where applicable), DQ observation, bandit feedback (PropertyCorrection only). Implemented: PropertyCorrection, Merge, Split, Add, Tombstone, RejectContribution.
- **Why separate:** This is the layer between API and persistence; calling out the orchestration cut keeps "what runs where" clear.
- **How to teach:** Annotated walk through `apply_property_correction` (the most fields-touched correction). Then a table mapping each correction type to (audit row + mutation + lineage + DQ + feedback) presence. References: `knot/graph/corrections.py`, `knot/api/graph/corrections.py`. Static markdown.

### 32. `data/trust-resolution.md` — Three policies, all deterministic  (static)
- **What:** `ARGMAX_TRUST` uses scalar per-source `trust_config` (human-set). `POSTERIOR_MEAN` uses the per-(source, slot) Beta posterior mean (learned). `LCB` uses `mean − k·stddev` (penalises uncertainty, conservative). All three are argmax-style; tiebreaks are alphabetical by source. Multivalued slots union across sources regardless of policy. Sampling/exploration policies were intentionally dropped — knot reads should be deterministic.
- **Why separate:** Trust is the user-visible payoff of the design; it earns a focused page.
- **How to teach:** Three tables of (source, slot, value) → resolved value, one per policy, computed by hand with worked posterior arithmetic. Then point at the `resolve_entity` function. References: `knot/graph/resolve.py`, `knot/db/trust_config.py`, `knot/db/trust_posteriors.py`. Static markdown.

### 33. `data/extensions-and-er.md` — The dispatcher pattern  (static)
- **What:** A tiny dispatcher (`_Dispatcher` in `extensions/__init__.py`) routes typed events to handlers. ER (entity resolution) is the first user: ingest emits `IngestResolveCanonical`; the default handler does identifier-slot passthrough; `@er.register("Movie")` per-class overrides.
- **Why separate:** Extensions are the only place readers will plug in code that affects ingest behavior. Putting them on their own page surfaces that.
- **How to teach:** Show a custom `er.register("Person")` handler that does fuzzy-name matching. Show the priority parameter on `dispatch.on`. Note the "side-effect import" pattern that auto-registers ER. References: `knot/extensions/__init__.py`, `knot/extensions/events.py`, `knot/extensions/er.py`, `knot/api/graph/ingest.py` (the call site). Static markdown.

### 34. `data/audit-and-lineage.md` — Immortal audit  (static)
- **What:** `_user_corrections` is the typed correction audit log (id, correction_type, payload JSONB, applied_by, applied_revision, created_at). `canonical_id_lineage` is the human-readable identity-event log (event_id, class, change_type, from_canonical_ids, to_canonical_ids, applied_revision, correction_id). Bindings carry `change_type` + `correction_id` so the row-level provenance roots back to a single audit entry.
- **Why separate:** Compliance/operations question; one page so it doesn't get hidden inside corrections orchestration.
- **How to teach:** One example: a Merge of `tt0001` into `tt0002`. Show the audit row, the lineage event, the bindings closed/opened, and a SQL query that walks correction → bindings → original source rows. References: `knot/db/corrections.py`, `knot/db/graph_store.py:append_lineage_event, list_lineage`, `knot/db/control_schema.sql`. Static markdown.

### 35. `data/data-quality.md` — DQ observations  (static)
- **What:** Two write paths: `record_incremental` runs in every ingest/correction request thread, emitting one row per affected stored slot tagged with the batch/correction id. `full_scan` aggregates the whole data plane on demand (`POST /dq/scan`). Reads via `query_observations` and `summarize`.
- **Why separate:** DQ is a separate subsystem with its own table and routes; teaching it elsewhere always crowds the page.
- **How to teach:** Show one ingest's DQ rows; then a full_scan row for the same source/class/slot. Compare null_rate, distinct_count over time. References: `knot/db/dq.py`, `knot/api/dq.py`, `knot/db/control_schema.sql:dq_observations`. Static markdown.

### 36. `api/overview.md` — REST surface map  (static)
- **What:** One table of every route, method, auth requirement, body shape (link to the detail page). The four routers: `auth`, `spec`, `graph`, `dq`, `lake`. Plus `/healthz`.
- **Why separate:** Operators will scan this page before reading any detail. It's a directory.
- **How to teach:** Generated table of contents. References: `knot/api/main.py`, all of `knot/api/`. Static markdown.

### 37. `api/auth-and-users.md` — Bearer tokens, dev mode  (static)
- **What:** `Authorization: Bearer <api_key>` → SHA-256 hash → users table lookup. `KNOT_AUTH_DEV_MODE=1` returns a synthetic `dev:default` principal. `KNOT_BOOTSTRAP_ADMIN_KEY` seeds an admin if the table is empty. The `/auth/users` admin surface (list, create, rotate, delete). Audit `applied_by` comes from the principal, not request bodies.
- **Why separate:** Auth is its own concern — operators set it up once and want a single page.
- **How to teach:** Curl example for first-time admin bootstrap. Then `POST /auth/users` to create a non-admin, rotate, delete. References: `knot/api/auth/auth.py`, `knot/api/auth/security.py`, `knot/db/users.py`, `knot/config/config.py`. Static markdown.

### 38. `api/spec-router.md` — `/spec/*`  (static)
- **What:** `GET /spec/published[/...]` reads. `GET /spec/revisions[/{n}]` immortal history. `GET/POST/DELETE /spec/drafts[/...]` mutate-in-place draft lifecycle. `POST /spec/drafts/{n}/{types|slots|classes|sources|constraints}` mutations. `POST /spec/drafts/{n}/publish?allow_destructive=…` runs the gate. `POST /spec/rollback/{n}` promotes a prior revision. Every mutation goes through `edit_draft` (row-locked).
- **Why separate:** The spec router is the most-used router; deserves its own catalog.
- **How to teach:** Endpoint table + one curl for each. Cross-link to the publish gate page (#29). References: `knot/api/spec.py`, `knot/db/spec_store.py`. Static markdown.

### 39. `api/graph-router.md` — `/graph/*`  (static)
- **What:** `POST /graph/ingest/{source}` (with optional `validate_constraints`), `GET /graph/classes/{cls}` + `/{cid}` + `/{cid}/resolved`, `POST /graph/corrections` (six discriminated types), `GET /graph/corrections` audit log, `GET/PUT /graph/trust[/...]` scalar scores, `GET/POST/DELETE /graph/trust/posteriors[...]`, `POST /graph/trust/feedback`, `POST /graph/constraints/check`, `GET/POST /graph/query` (GraphQL). Subrouter split: `ingest`, `reads`, `corrections`, `trust`, `constraints`, `graphql`.
- **Why separate:** Graph router is the data plane's surface; routes need their own catalog separate from spec.
- **How to teach:** Subsection per subrouter, one curl per route. References: `knot/api/graph/__init__.py`, `knot/api/graph/{ingest, reads, corrections, trust, constraints, graphql}.py`. Static markdown.

### 40. `api/constraints-translator.md` — JSON expression bodies  (static)
- **What:** `ExprJson` is an Annotated discriminated union with `kind` literals: `literal`, `slot_path`, `compare`, `bool_expr`, `within`, `between`, `matches`, `relation_all`, `relation_any`, `reverse_relation`, `relation_ref`, `filtered_relation`, `relation_project`, `relation_count`, `relation_aggregate`. `translate_expr(node_json, spec, primary)` walks the JSON, resolves slot/class names, returns a metaschema object.
- **Why separate:** This is the only "external schema" knot publishes; constraint authors authoring through the API need a complete reference.
- **How to teach:** Side-by-side table: SDK Python expression / metaschema object / JSON shape that lands on the API. References: `knot/api/constraint_translator.py`. Static markdown.

### 41. `api/graphql-endpoint.md` — `/graph/query`  (static)
- **What:** `GET /graph/query` returns Strawberry's bundled GraphiQL HTML (POSTs to its own URL). `POST /graph/query` accepts `{query, variables, operationName}` and runs against the schema cached by content_hash. Schema rebuilds when content_hash changes — operators don't reload.
- **Why separate:** GraphQL is a single endpoint with a UI; it earns a focused page rather than living inside the graph-router catalog.
- **How to teach:** Screenshot of GraphiQL with three saved queries (list, by canonical id, aggregate). One curl that POSTs the same. References: `knot/api/graph/graphql.py`, `knot/spec/compile/graphql/__init__.py`. Static markdown.

### 42. `api/lake-endpoint.md` — `/lake/materialize`  (static)
- **What:** `GET /lake/materialize` returns `{spec_revision, classes: [{name, current, history}, ...]}`. Optional `?class=Movie` filter. Skips abstract + defined classes.
- **Why separate:** Lake is operator-facing and rarely a request-time concern; calling it out separately keeps the graph-router page focused on consumers.
- **How to teach:** Curl + a sample response + three target-dialect wrappers (continuing from #26). References: `knot/api/lake.py`, `knot/spec/compile/postgres/lake.py`. Static markdown.

### 43. `api/dq-endpoint.md` — `/dq/*`  (static)
- **What:** `GET /dq/observations` time-series query (filters: source, class, slot, since, until, kind). `GET /dq/observations/summary` per-(source, class, slot) roll-up. `POST /dq/scan` runs a full_scan against the published spec.
- **Why separate:** Same as #35 (DQ is its own subsystem).
- **How to teach:** Curl + one filtered example (`?kind=full_scan&since=2026-05-01`). References: `knot/api/dq.py`. Static markdown.

### 44. `ops/docker-compose.md` — Dev stack  (static)
- **What:** `docker-compose.yml` runs postgres-16 (tmpfs, port 5432) and neo4j-5-community (apoc plugin, ports 7474+7687). knot itself is not in compose — readers run `uvicorn knot.api.main:app` against the postgres container. `scripts/up.sh`, `down.sh`, `wait-ready.sh` are convenience wrappers.
- **Why separate:** Dev setup deserves its own page.
- **How to teach:** Walk through "fresh clone → tests passing → notebook running" in five commands. References: `docker-compose.yml`, `scripts/`. Static markdown.

### 45. `ops/config-and-env.md` — `KNOT_*` env knobs  (static)
- **What:** Catalog every env var: `KNOT_CONTROL_DSN`, `KNOT_DEV_MODE`, `KNOT_AUTH_DEV_MODE`, `KNOT_BOOTSTRAP_ADMIN_KEY`, `KNOT_LOG_LEVEL`, `KNOT_LOG_FORMAT`, `KNOT_DATA_SCHEMA`, `KNOT_USER_CORRECTIONS_SOURCE`. `Settings` is pydantic-settings; defaults, dev-mode fallback DSN.
- **Why separate:** Every operator needs a flat reference for config knobs; doesn't belong nested in any other page.
- **How to teach:** Table: env var, default, what it does, when to change it. References: `knot/config/config.py`. Static markdown.

### 46. `ops/logging-and-request-ids.md` — Structured logs + access  (static)
- **What:** Two formats (`text` for dev, `json` for prod, default switches on `KNOT_DEV_MODE`). Every JSON record carries timestamp, level, logger, message + extras. `RequestIDMiddleware` reads/sets `X-Request-ID`, stores it in a `ContextVar`, emits one access-log line per request (skipping `/docs`, `/openapi.json`, `/auth/me`). Uvicorn's logging is replaced.
- **Why separate:** Operators integrating with log aggregators need this in one place.
- **How to teach:** Sample text and JSON access lines side-by-side. The exact uvicorn invocation (`--log-config /dev/null --no-access-log`). References: `knot/logging_config.py`, `knot/api/middleware.py`. Static markdown.

### 47. `ops/publishing-and-rollback.md` — Lifecycle runbook  (static)
- **What:** Real-world workflow: create draft, mutate, publish (with destructive-change consideration), roll back if needed. The four publish-gate phases (Pydantic, references, mixin/defined-class, constraint check). What `allow_destructive=true` actually does.
- **Why separate:** Operators need a page that reads as a runbook, not a reference.
- **How to teach:** Numbered steps with the curl for each. Failure modes section: "what does each `PublishGateError` mean and how do I fix it". References: `knot/api/spec.py`, `knot/db/spec_store.py`, `knot/spec/compile/postgres/migration.py`. Static markdown.

### 48. `ops/upgrades-and-migration.md` — Destructive change gate  (static)
- **What:** Which `Change` types are destructive (`DropClass`, `DropSlot`, `ChangeSlotType`, `DropDefinedClass`) and why. The `allow_destructive` flag's contract. Apply order (drops → concrete adds → defined adds) and why. What happens to bindings on a DropClass.
- **Why separate:** This is the page operators reach for when they're about to do something risky.
- **How to teach:** Each destructive change with a "before" and "after" and a recovery procedure (back to the prior revision via rollback, restore from snapshot, etc.). References: `knot/spec/compile/postgres/migration.py:is_destructive, apply_changes`. Static markdown.
