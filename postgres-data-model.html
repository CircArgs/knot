knot — the postgres data model

How a spec compiles to tables, what a row really looks like, and what migrations do underneath.

1. The mental model

knot is a compiler. The user writes an ontology spec — classes, slots, sources, constraints — and knot translates that into postgres DDL plus a small runtime that ingests rows, resolves multi-source conflicts, and emits GraphQL.

Three things are worth pinning down before any tables are explained:

  1. Two postgres schemas, two jobs. public holds what knot knows (the spec itself, audit logs, trust config). knot_data holds what knot stores (per-class fact tables compiled from the spec).
  2. Source rows are immortal; bindings tell the story. A row arrives from a source (imdb, tmdb, …) and lands in knot_data.<class> once and never moves. A second table, knot_data.<class>_bindings, holds the SCD2 history of which canonical-id that row currently maps to. Merges, splits, and corrections rewrite bindings — they don't rewrite source rows.
  3. Drafts are mutable, published revisions are frozen. Spec edits accumulate on a draft row in spec_revisions with published=FALSE. Publish flips that bit, runs the migration diff against the previous published revision, and emits DDL.

2. Two postgres schemas

schema public

The control plane. What knot knows.

  • spec_revisions — every draft and every publish
  • trust_config — per-source trust scores (runtime)
  • trust_posteriors — Beta posteriors for bandit resolution
  • _user_corrections — audit log of corrections
  • canonical_id_lineage — merge / split / add events
  • users — API key principals
  • dq_observations — data-quality stats per ingest

schema knot_data

The data plane. What knot stores.

  • knot_data.<class> — source-row facts (one per ingested row)
  • knot_data.<class>_bindings — SCD2 history of which row currently maps to which canonical_id

Every concrete (non-abstract) class on the published spec has these two tables. Created at publish time by the migration emitter; altered there too.

3. The control plane

spec_revisions

One row per authoring revision. Drafts are published=FALSE and mutable (updated in place). Published rows are frozen. A partial unique index enforces "at most one published row at a time".

CREATE TABLE spec_revisions (
    revision         SERIAL       PRIMARY KEY,
    spec             JSONB        NOT NULL,        -- full-fidelity Pydantic dump
    content_hash     CHAR(64)     NOT NULL,        -- canonical_dump → sha256
    published        BOOLEAN      NOT NULL DEFAULT FALSE,
    parent_revision  INT          REFERENCES spec_revisions(revision),
    label            TEXT,
    created_at       TIMESTAMPTZ  NOT NULL DEFAULT now(),
    published_at     TIMESTAMPTZ
);

CREATE UNIQUE INDEX spec_revisions_one_published
    ON spec_revisions (published) WHERE published = TRUE;
Why JSONB? The spec is a typed Pydantic tree with real object references between entities (slot → class, source → class, constraints with expression trees). knot serialises that tree to JSONB at publish, then rehydrates it from JSONB on every read. content_hash is a sha256 over the canonicalised JCS bytes so revision identity is content-addressable.

The other control tables (one-liners)

tablewhat it holds
trust_configPer-source scalar trust score, runtime-editable, used by ARGMAX_TRUST resolution.
trust_posteriorsPer-(source, slot) Beta posterior (alpha, beta); updated by correction feedback. Drives POSTERIOR_MEAN / LCB.
_user_correctionsImmortal audit log: every property correction / merge / split / add / tombstone, with payload + applied_revision.
canonical_id_lineageAppend-only event log of canonical_id transitions (merge / split / add / tombstone) — human-readable derived view of binding history.
dq_observationsPer-(source, class, slot) stats from every ingest batch and every full scan.

4. Per-class storage shape

For every concrete (non-abstract, non-defined) class on the published spec, knot emits two tables at publish time:

knot_data.<class>

Source-row facts. One row per (_source, _source_row_id) — what the source said.

System columns:

  • _knot_row_id UUID — stable internal anchor
  • _source TEXT — name of the Source that pushed the row
  • _source_row_id TEXT — source-native id (e.g. tt0111161)
  • _ingest_at TIMESTAMPTZ
  • _spec_revision INTEGER — FK to spec_revisions

Primary key: (_source, _source_row_id).
Plus one column per stored slot.

knot_data.<class>_bindings

SCD2 binding history. One row per (knot_row_id, valid_from) — "this row was bound to this canonical_id from then until valid_to".

Columns:

  • knot_row_id UUID — points to a row in the source table
  • canonical_id TEXT — current logical identity
  • valid_from TIMESTAMPTZ
  • valid_to TIMESTAMPTZ NULL — NULL means "currently active"
  • change_type TEXT — ingest / merge / split / correction
  • applied_revision INTEGER — FK to spec_revisions
  • correction_id INTEGER NULL — FK to _user_corrections if applicable

The two indexes that matter

indexpurpose
<cls>_bindings_current Partial index on (canonical_id) WHERE valid_to IS NULL — the hottest read path. Every "find the source rows for this canonical_id" lookup uses this.
<cls>_bindings_one_current_per_row Partial unique index on (knot_row_id) WHERE valid_to IS NULL — enforces the invariant that any given source row has at most one current binding. Catches race conditions in merge / split that escape FOR UPDATE.
The big idea. A read of a class's current state is a JOIN of the source table against the bindings table where valid_to IS NULL. An ER merge doesn't rewrite source rows — it closes one binding (UPDATE SET valid_to = now()) and opens another (INSERT with the new canonical_id and valid_to NULL). All history is preserved because closed bindings stay.

5. Type expression → postgres column type

Every slot in the spec carries a TypeExpression (a recursive sum: Primitive, Array(of=...), ClassRef(target_class=...)). The postgres compile dispatches over that tree to produce a column type from a whitelist — type names never get spliced raw into DDL.

TypeExpressionPostgres column type
Primitive("string")TEXT
Primitive("integer")INTEGER
Primitive("float")DOUBLE PRECISION
Primitive("boolean")BOOLEAN
Primitive("datetime")TIMESTAMPTZ
Primitive("date")DATE
Array(of=Primitive("string"))TEXT[]
Array(of=Primitive("integer"))INTEGER[]
ClassRef(target_class=Movie)TEXT (holds a canonical_id)
Array(of=ClassRef(...))TEXT[]
None (derived / untyped)TEXT (default)
Why ClassRef is just TEXT. A class-reference slot stores the target's canonical_id, not a numeric FK. This is deliberate: canonical_ids are stable across merges (the bindings table changes, the value in the column doesn't), and they're meaningful to humans (imdb:tt0111161 beats 17394). Joins happen via knot_data.<target>_bindings.canonical_id with valid_to IS NULL.

Derived slots are skipped

A slot with a non-None derivation (a RelationCount, RelationAggregate, etc.) gets no column. The value is computed at query time. The migration emitter calls is_stored(slot) when walking effective slots and only emits columns for stored ones.

6. Walkthrough: a Movie scenario

Here's a concrete spec. Three sources for movies: imdb, tmdb, wiki. Each source has its own native identifier slot — because ER hasn't happened yet, we don't pretend they share an id.

# Pydantic spec construction
imdb_id   = Slot(name="imdb_id",   type=Primitive(name="string"), identifier=True, required=True)
tmdb_id   = Slot(name="tmdb_id",   type=Primitive(name="string"), identifier=True)
wiki_slug = Slot(name="wiki_slug", type=Primitive(name="string"), identifier=True)
title     = Slot(name="title",     type=Primitive(name="string"))
year      = Slot(name="year",      type=Primitive(name="integer"))
genres    = Slot(name="genres",    type=Array(of=Primitive(name="string")))

Movie = OntologyClass(name="Movie", slots=[imdb_id, tmdb_id, wiki_slug, title, year, genres])

imdb_src = Source(name="imdb", entity_class=Movie, identifier_slot=imdb_id,   trust_score=0.9)
tmdb_src = Source(name="tmdb", entity_class=Movie, identifier_slot=tmdb_id,   trust_score=0.7)
wiki_src = Source(name="wiki", entity_class=Movie, identifier_slot=wiki_slug, trust_score=0.5)

spec = Spec(id="media", version="1.0.0",
            slots=[imdb_id, tmdb_id, wiki_slug, title, year, genres],
            classes=[Movie],
            sources=[imdb_src, tmdb_src, wiki_src])

What knot creates at publish time

-- 1. Source-row table
CREATE TABLE knot_data.movie (
    _knot_row_id    UUID        NOT NULL DEFAULT gen_random_uuid() UNIQUE,
    _source         TEXT        NOT NULL,
    _source_row_id  TEXT        NOT NULL,
    _ingest_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    _spec_revision  INTEGER     NOT NULL REFERENCES public.spec_revisions(revision),
    PRIMARY KEY (_source, _source_row_id),

    imdb_id     TEXT     NULL,
    tmdb_id     TEXT     NULL,
    wiki_slug   TEXT     NULL,
    title       TEXT     NULL,
    year        INTEGER  NULL,
    genres      TEXT[]   NULL
);

-- 2. Bindings table (SCD2)
CREATE TABLE knot_data.movie_bindings (
    knot_row_id        UUID        NOT NULL,
    canonical_id       TEXT        NOT NULL,
    valid_from         TIMESTAMPTZ NOT NULL DEFAULT now(),
    valid_to           TIMESTAMPTZ,
    change_type        TEXT        NOT NULL,
    applied_revision   INTEGER     NOT NULL REFERENCES public.spec_revisions(revision),
    correction_id      INTEGER     REFERENCES public._user_corrections(id),
    PRIMARY KEY (knot_row_id, valid_from)
);

-- 3. Indexes
CREATE INDEX movie_bindings_current
    ON knot_data.movie_bindings (canonical_id) WHERE valid_to IS NULL;

CREATE UNIQUE INDEX movie_bindings_one_current_per_row
    ON knot_data.movie_bindings (knot_row_id) WHERE valid_to IS NULL;

Notice what is not there: no movies plural, no per-source tables. The class name lowercased is the table name. All three sources write into the same knot_data.movie table; _source distinguishes them.

7. What happens at ingest

An ingest call looks like:

POST /graph/ingest/imdb
{
  "rows": [
    { "imdb_id": "tt0111161", "title": "The Shawshank Redemption", "year": 1994 },
    { "imdb_id": "tt0068646", "title": "The Godfather",            "year": 1972 }
  ]
}

knot's ingest_rows does this in one transaction:

  1. Validate rows with a Pydantic model built from the source's class (typed fields, required-slot checks). Failures abort with 422.
  2. Fire RowsIngesting on the extension dispatcher. Team-written ER may run, set canonical_ids. If KNOT_ER_URL is set, the built-in ER shim POSTs to the sibling er/ service.
  3. Default canonical_id if nothing was set: {source_name}:{source_row_id}. So an imdb row with imdb_id="tt0111161" gets canonical_id imdb:tt0111161. Debuggable; ER can collapse it later.
  4. INSERT rows into knot_data.movie + bindings rows into knot_data.movie_bindings. Re-pushing the same (_source, _source_row_id) updates the existing row in place — the binding is preserved (no new row in the bindings table) so the canonical_id stays.
  5. Optional constraint check if ?validate_constraints=true. Compiles every ERROR-severity constraint whose primary class matches this source's class, runs it, raises 422 on any violation, transaction rolls back.
  6. DQ recording: row count, null count, distinct count, min/max per slot get appended to dq_observations tagged with this ingest's batch_id.
  7. Fire RowsIngested on the extension dispatcher (post-insert audit hooks).

8. ER merges — SCD2 in action

ER decides tmdb:278 is the same as imdb:tt0111161. The merge API closes the losing binding and opens a new one pointing the same source row at the surviving canonical_id. Source data is never touched.

-- Inside graph_store.merge_canonical_ids():
UPDATE knot_data.movie_bindings
   SET valid_to = now()
 WHERE canonical_id = 'tmdb:278' AND valid_to IS NULL;

INSERT INTO knot_data.movie_bindings
       (knot_row_id, canonical_id, valid_from, valid_to,
        change_type, applied_revision)
SELECT knot_row_id, 'imdb:tt0111161', now(), NULL,
       'merge', <current_revision>
  FROM knot_data.movie_bindings
 WHERE canonical_id = 'tmdb:278'
   AND valid_to IS NOT NULL
   AND valid_to = (-- the row we just closed
       SELECT max(valid_to) FROM ...);

-- Plus an event row in canonical_id_lineage:
--   from_canonical_ids = ['tmdb:278'], to_canonical_ids = ['imdb:tt0111161']
knot_data.movie_bindings (after merge)
knot_row_idcanonical_idvalid_fromvalid_tochange_type
uuid-a1…imdb:tt0111161t₀NULLingest
uuid-b2…imdb:tt0068646t₀NULLingest
uuid-c3…tmdb:278t₀t₁ingest
uuid-c3…imdb:tt0111161t₁NULLmerge

Reading knot_data.movie for canonical_id = 'imdb:tt0111161' now returns two source rows: the original imdb one and the tmdb one — both contribute to that entity. Resolution policy on a slot decides which value wins for multi-source conflicts.

SCD2 invariant: for any knot_row_id, there is at most one row with valid_to IS NULL. Enforced by a partial unique index. A split operation does the inverse — opens multiple new bindings out of one closed one.

9. User corrections

Six correction operations are wired in. Each lands as an audit row in _user_corrections and a data-plane effect.

operationdata-plane effect
propertyUpsert a row in knot_data.<class> tagged _source = '_user_corrections' with just the corrected slot value. Bumps the Beta posteriors for the original sources (agreement → α++, disagreement → β++).
mergeClose N bindings; open 1 binding to the surviving canonical_id. Emits a canonical_id_lineage event. Cross-class ClassRef columns that pointed at the merged-away id get UPDATE-rewritten.
splitClose 1 binding; open N new bindings partitioned by source.
addInsert a synthetic source row tagged _source = '_user_corrections', open one binding to a brand-new canonical_id.
tombstoneClose the current binding; never open a replacement. include_tombstoned=True on reads can still surface the rows.
reject_contributionClose just the binding from one specific source. The canonical_id survives if other sources still contribute.

The _user_corrections source-name is a synthetic value — there's no Source entity in the spec for it. It's just a sentinel in the _source column so corrections are distinguishable from source-pushed facts.

10. How migrations work

When the user publishes a draft, knot:

  1. Loads the previous published spec from JSONB.
  2. Diffs previous vs. candidate via diff_specs(), producing a list of typed Change dataclasses.
  3. Classifies each change into one of three buckets (below).
  4. Gates on:
    • Any Bucket A (DDL-destructive) change without allow_destructive=true → reject with PublishGateError.
    • Any new or changed constraint that fails over current data → reject.
  5. Emits DDL via emit_ddl() — single-dispatch on the Change subtype, runs the corresponding postgres statement.
  6. Updates spec_revisions: published = TRUE on the draft, FALSE on the previous (via the partial unique index).

The three buckets

A — DDL-destructive

Storage shape changes that can lose data. Refused unless allow_destructive=true.

DropClass, DropSlot, DropDefinedClass, DropSource, ChangeSlotTypeExpression, ChangeClassAbstract, ChangeSourceEntityClass, ChangeSourceIdentifierSlot.

B — Data-revalidation

Constraint tightens; old data may now violate. No DDL, but the publish gate runs the constraint check over current data.

ChangeSlotPattern, ChangeSlotPermissibleValues, ChangeSlotMinimum, ChangeSlotMaximum, ChangeConstraintBody.

C — Spec-only / runtime

No DDL, no data revalidation. Audit records.

ChangeSlotResolutionPolicy, ChangeConstraintSeverity, ChangeSourceTrustScore, ChangeSourceSlotPrior, ChangeClassMixins, ChangeClassIsA (concrete classes), AddSource, etc.

11. The Change-type catalog

What each change emits, end-to-end. cls means the candidate-side class object.

Class-level

ChangeBucketDDL emitted
AddClass(cls) C CREATE TABLE knot_data.<cls> + bindings table + 2 indexes
DropClass(class_name) A DROP TABLE knot_data.<cls>_bindings CASCADE + DROP TABLE knot_data.<cls> CASCADE
AddDefinedClass(cls) C CREATE OR REPLACE VIEW knot_data.<cls> AS … over the parent class with the compiled definition body as WHERE.
DropDefinedClass A DROP VIEW IF EXISTS knot_data.<cls> CASCADE
ChangeClassAbstract A abstract → concrete: same as AddClass. concrete → abstract: refuses on non-empty table; otherwise DROP TABLEs.
ChangeClassIsA C Concrete: no-op (is_a doesn't drive DDL — own table, own slots). Defined: re-emit the VIEW with the new parent.
ChangeClassMixins C Audit-only. The actual column adds/drops ride on AddSlot/DropSlot records.
ChangeClassDefinition C CREATE OR REPLACE VIEW — idempotent, no data loss.

Slot-level

DropSlot(cls, slot_name) A ALTER TABLE knot_data.<cls> DROP COLUMN <slot>
ChangeSlotTypeExpression(slot, prev_pg_type, new_pg_type) A ALTER TABLE … ALTER COLUMN <slot> TYPE <new> USING <slot>::<new>. Aborts the whole migration if any row's cast fails.
ChangeSlotRequired C None — API-enforced (correction rows are partial).
ChangeSlotPattern / PermissibleValues / Minimum / Maximum B None. Publish gate revalidates current data against the new constraint.
ChangeSlotIdentifier C None — storage PK is (_source, _source_row_id); the identifier flag is ER/SCD2 advisory.
ChangeSlotResolutionPolicy C None — query-time behavior.
ChangeSlotDerivation C None — derivations are query-time projections.

Source-level

12. The publish gate

Two gates run before any DDL touches postgres:

Gate 1 — Destructive change refusal. If any change in the diff is in _DESTRUCTIVE_CHANGE_TYPES and the caller did not pass allow_destructive=true, publish fails with PublishGateError("destructive change without allow_destructive: …"). The draft stays in place; nothing in postgres changes.
Gate 2 — Constraint revalidation. For every constraint that was added or changed, knot compiles its SQL body and runs it against the current published data. Any rows that would violate the constraint after publish are reported as PublishGateError("constraint violations: …"). Same as Gate 1: draft stays, nothing changes.

Only if both gates pass does apply_migration walk the change list and call emit_ddl for each one inside a single transaction. If any DDL fails, the whole publish aborts and rolls back — postgres atomic DDL.

What about the spec_revisions row itself?

The draft row already exists (created by POST /spec/drafts and mutated by every POST /spec/drafts/{id}/...). Publish sets published = TRUE and published_at = now(). The partial unique index forces the previous published row (if any) to flip to FALSE in the same transaction.

13. Cheat sheet

For talking-points / explaining-to-someone-else:

QuestionAnswer
"Where is the schema?"knot_data.<class.name.lower()> for source rows, knot_data.<cls>_bindings for SCD2 history. The spec itself lives in public.spec_revisions as JSONB.
"How are merges represented?"Close the losing binding (valid_to = now()); open a new binding pointing the same knot_row_id at the surviving canonical_id. Source data is never moved.
"How are types mapped?"Recursive walk of Slot.type: Primitive via whitelist, Array appends [], ClassRef is always TEXT (holds a canonical_id).
"How do you handle nullability?"Every slot column is NULL-able regardless of required=True. Correction rows are partial by construction (they update one slot), so column-level NOT NULL would break them. required is enforced at the API layer.
"How are derived slots stored?"They aren't. is_stored(slot) returns False when derivation is non-None; no column is emitted. The GraphQL layer computes them as correlated subqueries at query time.
"What happens if I rename a slot?"The diff sees DropSlot + AddSlot. Bucket A → publish refuses without allow_destructive. There's no rename track-record because the canonical name in the spec is the only identity a slot has.
"How are migrations atomic?"All DDL for a publish runs in one transaction. Postgres supports transactional DDL — any failure rolls back the whole publish.
"What's the difference between abstract and defined classes?"Abstract: not concrete, no table. Used as a mixin or is_a parent. Defined: has a body (a predicate over a parent class); compiled to a VIEW over the parent's table.
"What's _user_corrections in _source?"Synthetic source-name sentinel for correction rows. No Source entity for it exists in the spec; it's a hardcoded constant for separating user-pushed facts from source-pushed facts.
