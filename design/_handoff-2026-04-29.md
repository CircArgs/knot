### Decision 1 — Source enum-map dispatcher (replaces 1:1 source-to-class)

A single source can produce rows that route to multiple classes via an explicit discriminator column. Mapping lives on the source node. Strict over enum values: every value must either map to a class or to `drop: true`; unmapped values fail the run loudly. Wildcard `"*": {drop: true}` is the explicit opt-in laxity.

**Two shapes** for the source node:

```yaml
# Heterogeneous (general)
discriminator: role
mappings:
  actor: {ontology_class: Person, fields: {...}}
  director: {ontology_class: Director, fields: {...}}
  casting_director: {drop: true}
```

```yaml
# Homogeneous shorthand (single class)
mapping:
  ontology_class: Movie
  fields: {tt_id: source_natural_key, ...}
```

**Replaces** the implicit "subclass-tree expansion at compile time" idea I floated and the user rejected. Subclass-ness is an ontology-graph fact (used for derived views/queries); source routing is explicit via discriminator.

**Action:** revise `source-layer-contract.md` to document this. The existing text (single `ontology_class` field + flat mapping) is the homogeneous shorthand; the heterogeneous form is the general case.

### Decision 2 — Cross-class data-dependency pinning for relation classes

Relation classes (e.g., `ActedIn` referencing Movie + Person ids) pin their parent classes' run hashes at compile time, not just spec revisions. Replay reads the pinned snapshots, not current state.

`WorkflowSpec` for a relation class grows:

- A top-level `pinned_parent_runs: {Movie: {hash, run_id, completed_at}, Person: {...}}`
- Resolve and DQ tasks receive `endpoint_class_runs: {Movie: hash, Person: hash}` in their params
- The team's `LakeReader` impl reads the parent class's resolved-entity output AT THE PINNED HASH, not current

Compile-time choice: default is "most-recent-successful run of each parent class" (implicit but predictable); override is `?parents={Movie: hash_X, Person: hash_Y}` query param (caller specifies; useful for replay or A/B). Both produce different compiled hashes (parents are in canonical form).

**Action:** write a new `design/cross-class-pinning.md` and update `compiled-workflow-hashing.md` to reference it.

### Decision 3 — Joint ER (er_cluster) as a SEPARATE mechanism from subclassing

Two distinct mechanisms, two distinct triggers:

| Concern | Mechanism |
|---|---|
| One source has rows for multiple classes | enum-map dispatcher on the source (Decision 1) |
| Multiple classes share an ER scope (e.g., Author + Editor + Translator are all roles a Person can take) | explicit `er_cluster` ontology node listing the classes |
| One class is-a another (Director is-a Person) | ontology-graph fact; **not** a pipeline mechanism. Per-class runs stay separate; subclass-ness is a derived view of the entity, not a runtime scope expansion. |

Joint ER is **not yet locked** — it's design intent. Open questions remain (cluster vs. trigger param; class in multiple clusters; per-class triggers interacting with existing cluster decisions). Captured for future locking, not for the v1 contract.

**Action:** when writing `design/entity-resolution.md` (which doesn't exist yet — I deleted a stale draft mid-session), include joint ER as an "explanatory, not yet locked" section with these open questions called out explicitly.

### Decision 4 — DQ semantics are the team's problem

After two pushbacks from the user, the right contract is minimal:

- Knot's compiler emits a `validate` stage in every per-class workflow
- The validate stage invokes `DqRunner.validate(class, run_context)` via the bound impl
- That's it. **No `dq_check` ontology node kind. No DQ payload schema. No check-kind enum (volume / freshness / distribution / SQL).**
- The team's `DqRunner` impl IS the DQ system — Great Expectations, Soda, dbt tests, custom, whatever
- Knot records pass/fail/diagnostics in audit; orchestrator's standard upstream-failure handling propagates fail to publish

The instinct to enumerate check kinds = knot stepping over the seam. Same pattern as `Orchestrator` and `MergeEngine`: knot owns the seam, the team owns the semantics.

**Action:** when documenting DQ, write **one paragraph**, not a half-page, in whichever doc covers pipeline stages. Resist the urge to model anything.
